# Issue Workflow

## 1. Створення Issue

Кожна окрема задача, помилка або запит на зміну функціональності повинні бути представлені окремою Issue.

Issue повинна містити:
- зрозумілий заголовок;
- опис задачі;
- основні вимоги;
- критерії приймання (за необхідності);
- відповідні labels.

## 2. Labels

Labels використовуються для класифікації задач. Одна Issue може мати декілька labels.
Labels:
- `bug` — помилка;
- `documentation` — покращення або доповнення до документації
- `help wanted` — потрібна додаткова увага
- `feature` — новий функціонал
- `enhancement` — покращення вже існуючої функції
- `frontend` — завдання по інтерфейсу
- `backend` — серверна логіка, API, БД
- `testing` — написання та виправлення тестів
- `refactor` — покращення коду без зміни функціональності
- `security` — права доступу, авторизація, захист даних
- `authentication` — реєстрація, логін, сесії
- `realtime` — спільне редагування та WebSocket
- `wontfix` - задача більше не буде реалізована

## 3. Assignees

Для кожної задачі призначається відповідальний учасник команди. Відповідальний учасник працює над Issue та оновлює її статус у разі необхідності.

## 4. Робота над Issue

Перед початком роботи учасник:
1. перевіряє опис Issue;
2. створює окрему гілку;
3. виконує задачу;
4. за потреби оновлює Issue.

## 5. Pull Request

Після завершення задачі створюється Pull Request.

Pull Request повинен містити посилання на відповідну Issue.

Наприклад:

Closes #15

Це дозволяє автоматично закрити Issue після успішного
злиття Pull Request.

## 6. Закриття Issue

Issue закривається після:
- завершення реалізації;
- проходження перевірки коду;
- успішного злиття відповідного Pull Request.
Якщо задача більше не буде реалізована, Issue може бути закрита з відповідним поясненням та label `wontfix`.
