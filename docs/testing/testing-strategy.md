# Стратегія тестування NoteLy

**Мета й підхід.** Стратегія розвивається разом із NoteLy за V-моделлю:
вимоги ↔ приймальні, системний дизайн ↔ системні, архітектурні стики ↔
інтеграційні, компоненти ↔ модульні тести. Автоматизація перевіряє
відповідність специфікації, а приймання з користувачами — їхнім потребам.
Дотримуємося піраміди: багато модульних, менше інтеграційних і кілька
наскрізних тестів.

**Поточний стан і покриття.** На 31.10.2026 реалізований обсяг охоплює IAM
(автентифікація, ролі, режим «За посиланням», запити на доступ), документи з
кошиком і абзацами, пошук, календар подій і зберігання в PostgreSQL. Набір
pytest містить **392 тести**; останній локальний прогін із тестовою базою
PostgreSQL (`TEST_DATABASE_URL`) успішний: **95,86% покриття рядків і гілок**
`src` при порозі 90%. Тестові дублери ізолюють час, хешування, пошту й
метрики; адаптери PostgreSQL і міграції перевіряються на окремій тестовій
базі (фікстура `pg_pool` у `tests/conftest.py`; її використовують
`tests/db/`, адаптери IAM, документів, пошуку й календаря та
`tests/api/test_postgres_bootstrap.py`), а без `TEST_DATABASE_URL` ці тести позначаються як пропущені.
Клієнтські/WebSocket-сценарії ще не реалізовані.

Залишилося **60 непокритих рядків** та частково непокриті гілки. Запис OpenAPI
й `lifespan` — інфраструктура, специфікацію перевіряє окремий workflow.
Найбільше непокритих рядків у `src/iam/service.py` (8), `src/api/calendar.py`
і `src/documents/postgres.py` (по 6): варто покрити некоректні параметри
календаря й невідомі помилки API; захисні гілки гонок та недосяжних станів
мають нижчий пріоритет.
Деталі — у [звіті про тестування](./test-report.md).

**Плани за рівнями.**

- **Модульні — зараз і надалі:** розробники перевіряють бізнес-правила,
  валідацію й граничні випадки ізольовано. Нові правила супроводжуються
  тестами; поріг покриття — 90%.
- **Інтеграційні — при розширенні архітектури:** перевіряти стики
  FastAPI ↔ IAM, API ↔ БД/пошта, WebSocket ↔ автентифікація та права.
  Перевіряти контракти, транзакції, відмови й повтори з тестовою БД та
  контрольованими дублерами. Повний набір — при злитті та щоночі.
- **Системні:** коли буде зібраний повний клієнт-серверний продукт,
  перевіряти у production-подібному середовищі шлях від реєстрації до
  редагування, збереження, пошуку та спільного доступу; додати сценарій
  синхронізації десяти редакторів. Критичні smoke-тести — перед релізом,
  повний набір — щоночі.
- **Приймальні:** представники команди/зацікавлені користувачі проходять
  критерії user stories на alpha/beta-збірці й підтверджують готовність до
  розгортання. Фіксувати результат і дефекти; технічне покриття не замінює
  приймання.

**Нефункціональні та дослідницькі перевірки.** CI вже запускає Bandit і
`pip-audit`; доповнити перевірками авторизації, секретів у журналах і
загроз із [моделі загроз](../architecture/threat-model.md). Locust-сценарії
для NFR-PERF-002–005 не входять у CI: їх запускають вручну/перед релізом.
Команди й автоматична перевірка p95-порогів наведені нижче. Окремий
сценарій із p95 150 мс для змішаного навантаження також зберігається.
Property-based тестів поки немає; оцінити Hypothesis для нормалізації email,
політик сесій, ACL та ідемпотентності.

**Locust-перевірки NFR продуктивності.** Спочатку встановіть
`requirements-loadtest.txt` і запустіть API на `http://localhost:3000`
(див. інструкцію запуску в README). Кожний сценарій сам створює тестового
користувача; пошук створює рівно 100 документів у його робочому просторі.
Прогін завершується з ненульовим кодом, якщо p95 перевищує поріг або є
помилки. Вивід містить median, p95, p99 і max; `--csv` зберігає статистику.

```bash
python3 -m locust -f loadtests/search_locustfile.py --headless -u 1 -r 1 -t 30s --host http://localhost:3000 --csv /tmp/nfr-perf-005
python3 -m locust -f loadtests/auth_locustfile.py --headless -u 1 -r 1 -t 30s --host http://localhost:3000 --csv /tmp/nfr-perf-004
python3 -m locust -f loadtests/rename_locustfile.py --headless -u 1 -r 1 -t 30s --host http://localhost:3000 --csv /tmp/nfr-perf-002
python3 -m locust -f loadtests/restore_locustfile.py --headless -u 1 -r 1 -t 30s --host http://localhost:3000 --csv /tmp/nfr-perf-003
```

| NFR | Вимірюваний запит | Поріг p95 |
|---|---|---:|
| NFR-PERF-005 | `GET /api/v1/search?q=locustsearch`, 100 документів | ≤ 2000 мс |
| NFR-PERF-004 | `POST /api/v1/auth/login`, 30 успішних входів | ≤ 2000 мс |
| NFR-PERF-002 | `PUT /api/v1/documents/{id}` | ≤ 1000 мс |
| NFR-PERF-003 | `POST /api/v1/documents/{id}/restore` | ≤ 2000 мс |

**CI/CD і артефакти.** GitHub Actions на кожен push і pull request запускає
Black, Flake8, Bandit, pytest із покриттям ≥90% та `pip-audit`; помилка
блокує збірку. Далі додати інтеграційні тести на злиття, нічний набір і
системні/навантажувальні перевірки перед релізом. Пов'язувати вимоги й тести
через [матрицю простежуваності](../requirements/rtm.md); результати та межі
фіксувати у [переліку крайових випадків](./edge-cases.md) і звітах.

### Бонус — Ворота покриття в CI (Ольга Бідочка)

В проекті реалізовано автоматичне “ворота покриття” в CI: після кожного pull request запускається pipeline, який виконує `pytest` з підрахунком покриття (`--cov`), і збірка завершується з помилкою, якщо покриття коду нижче встановленого порогу. У конфігурації coverage поріг задано як:

```toml
[tool.coverage.report]
fail_under = 90
```

Тому будь-який PR з покриттям нижче 90% автоматично блокується до виправлення. Порог вибрано 90% не випадково: це відповідає критерію виходу, зафіксованому в плані тестування (src має мати покриття не нижче 90%), і одночасно є достатньо високим, щоб виявляти регресії, але не надто суворим для проекту на поточному етапі розвитку. Крім того, вимірювання ведеться саме для src, а режим branch = true забезпечує контроль не лише рядків коду, а й виконання гілок умов.

Це не лише документовано, а й підтверджено практикою: в репозиторії є успішний прогін для PR<https://github.com/ukma-fin-ssdm-2026/noproblem/pull/171> — Enforce test coverage threshold in CI, де зібрання пройшло після розгортання воріт покриття в CI. Отже, інтеграція покриття в пайплайн працює, а поріг 90% є поточним стандартом якості, який команда використовує як автоматичний бар’єр перед злиттям змін.
