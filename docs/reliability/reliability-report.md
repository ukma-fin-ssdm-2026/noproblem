## 2. Виправлені проблеми

### №7. Очищення кошика в обробці запиту → фоновий планувальник

**Ланцюг.** Несправність: `_purge_expired_trash()` викликався з `create()`, `list_trash()` і `restore()` і видаляв усі прострочені документи одним `DELETE`. Помилка: звичайний запит тримав транзакцію й з'єднання з пулу, поки видалялися чужі документи; збій очищення ставав збоєм самого запиту. Відмова: користувач, який просто створює документ чи відкриває кошик, отримував повільну відповідь або `500`.

**Обраний режим відмови.** Тут дві різні ситуації, тому й два режими:

| Ситуація | Режим | Чому |
|---|---|---|
| БД недоступна під час очищення | **Безпечна відмова** | Очищення — фонова службова дія. Краще відкласти її на годину, ніж зупинити планувальник; користувач цього не помічає |
| Некоректне значення `TRASH_PURGE_INTERVAL_S` | **Швидка відмова** | Інакше застосунок мовчки працював би без очищення кошика (мовчазний збій, категорія D); краще не стартувати й показати причину |
| Дефект у коді (не помилка БД) | **Швидка відмова** | Баг не можна ховати: цикл пише його в журнал і зупиняється |

**До** (`src/documents/service.py`, кожен із трьох методів):

```python
def create(self, user_id, idempotency_key, title):
    now = self._clock.now()
    self._purge_expired_trash(now)   # видалення ВСІХ прострочених документів
    ...

def _purge_expired_trash(self, now: datetime) -> None:
    self._documents.purge_trashed_before(now - TRASH_RETENTION)
```

**Після.** Очищення винесено в окремий модуль `src/scheduler/`.

Один запуск (`src/scheduler/service.py`) — вузький `except` і логування:

```python
def run_once(self) -> int:
    cutoff = self._clock.now() - TRASH_RETENTION
    try:
        purged = self._documents.purge_trashed_before(cutoff)
    except psycopg.Error:
        logger.exception(
            "Не вдалося очистити кошик; повторна спроба під час "
            "наступного запуску планувальника."
        )
        return 0
    ...
    return len(purged)
```

Фоновий цикл (`src/scheduler/loop.py`), який `lifespan` запускає раз на годину:

```python
async def run_periodically(purger: TrashPurger, interval_s: float) -> None:
    while True:
        await asyncio.sleep(interval_s)
        try:
            await asyncio.to_thread(purger.run_once)
        except Exception:
            logger.exception(
                "Планувальник зупинено через непередбачену помилку."
            )
            raise
```

Запити більше не очищують кошик, а лише ховають прострочені документи (`src/documents/service.py`):

```python
return self._documents.list_trashed(
    restorable,
    limit,
    offset,
    deleted_after=self._clock.now() - TRASH_RETENTION,
)
```

**Застосовані патерни.**

- **Винесення довгої операції з обробника запиту** — головне виправлення: очищення виконується у фоні й не впливає на час відповіді.
- **Вузький catch-блок** — перехоплюється лише `psycopg.Error` (зокрема `PoolTimeout`); `TypeError` та інші дефекти вилітають назовні.
- **Логування проблеми** — збій БД і зупинка циклу записуються в журнал `notely.scheduler`.
- **Захисні перевірки входу** — `trash_purge_interval_from_env()` відхиляє нечислові, від'ємні, `nan` та `inf` значення.
- **Неблокувальний виклик** — синхронне очищення виконується через `asyncio.to_thread`, щоб не блокувати event loop (урок знахідки №4).

**Що бачить користувач під час збою.** Нічого: кошик і відновлення працюють як завжди. Прострочені документи не показуються й не відновлюються, навіть якщо фізично ще лежать у базі, бо `list_trash()` і `restore()` самі перевіряють 30-денний термін.

**Як система повертається до норми.** Автоматично: наступний запуск планувальника (за замовчуванням через годину) видаляє все, що накопичилося. Ручне втручання потрібне лише при хибному налаштуванні інтервалу (виправити змінну й перезапустити) або при дефекті в коді (лог «Планувальник зупинено»).

**Обмеження.** В одному місці очищення під час запиту лишилося. Якщо користувач повторює `POST /documents` зі своїм старим `Idempotency-Key`, а документ із цим ключем уже пролежав у кошику 30 днів, але планувальник ще не видалив його, `create()` викликає `purge_trashed_before(now − 30 днів)` і лише потім створює новий документ. Без цього повтор повернув би вже «видалений» документ.

- **Що видаляється:** прострочені документи всіх користувачів, які накопичилися з останнього успішного запуску планувальника. Коли планувальник працює, це документи, що прострочилися щонайбільше за один інтервал (за замовчуванням годину), тобто одиниці, а не весь накопичений кошик, як до виправлення.
- **Коли обсяг може бути великим:** планувальник вимкнено (`TRASH_PURGE_INTERVAL_S=0`), він зупинився через дефект (у журналі є «Планувальник зупинено») або застосунок довго не працював. Ці стани видно в журналі чи конфігурації, і виправляються вони відновленням планувальника.
- **Збій БД на цьому шляху** не перехоплюється: саме цей запит отримує `500`, як і будь-яка інша операція з недоступною БД. Повтор запиту пізніше спрацює.
- **Наскільки це ймовірно:** за призначенням ключа ідемпотентності клієнт генерує новий ключ для кожної нової дії; той самий ключ повторюється лише при повторі запиту після збою мережі, тобто через секунди. Щоб потрапити на цей шлях, ключ треба повторити більш ніж через 30 днів.

Окремий метод видалення одного документа в порті сховища прибрав би й цей випадок, але потребує змін порту, обох адаптерів і тестів. Для ризику такого рівня це непропорційно, тому ми цього не робили.

**Тести** (`tests/reliability/`):

| Тест | Тип | Що перевіряє |
|---|---|---|
| `test_db_failure_is_logged_and_retried_next_run` | Обробка помилки, ін'єкція збою | Дублер сховища кидає `OperationalError` / `PoolTimeout` → `run_once` не падає, пише в лог, наступний запуск видаляє документи |
| `test_code_defect_is_not_hidden` | Обробка помилки | `TypeError` не перехоплюється |
| `test_purges_only_documents_older_than_30_days` | Межа 30 днів | 30 днів — видалено, 29 — ні |
| `test_loop_*` (2 тести) | Обробка помилки | Цикл працює до скасування; при дефекті пише в лог і зупиняється |
| `test_scheduler_interval.py` | Граничний | Допустимі (`""`, `0`, `0.5`, `" 30 "`) і недопустимі (`abc`, `-1`, `nan`, `inf`) значення інтервалу |

Додатково `tests/documents/test_repositories.py::test_list_trashed_hides_documents_deleted_before_cutoff` перевіряє фільтр кошика на сховищі в пам'яті й на PostgreSQL.

### №5. Пошук у PostgreSQL без обмежень

**Ланцюг.** До виправлення запит пошуку не мав SQL-ліміту чи тайм-ауту, а `fetchall()` завантажував усі збіги в пам'ять. На великій кількості доступних документів та абзаців повний пошук міг довго займати з'єднання і вичерпувати пул.

**Після.** `PostgresSearchRepository.find_matches()` у межах транзакції встановлює `SET LOCAL statement_timeout = '2s'`. SQL обмежує набір повернених документів параметром `LIMIT %s`; сервіс передає ліміт `MAX_SEARCH_RESULTS` (20). Обмеження локальне для транзакції, тому не впливає на наступних користувачів пулу.

Для контрольованої відмови адаптер перехоплює лише `psycopg.errors.QueryCanceled` (перевищено тайм-аут запиту) і `PoolTimeout` (не вдалося отримати з'єднання). Він записує помилку в журнал `notely.search` і кидає `SearchUnavailableError`. Інші неочікувані помилки не маскуються. HTTP-обробник перетворює доменну помилку на `503 Service Unavailable` з повідомленням «Пошук тимчасово недоступний. Спробуйте пізніше.» — порожній список не видається за успішний результат.

**Що бачить користувач і відновлення.** Якщо база надто повільна або пул вичерпаний, користувач отримує зрозумілу тимчасову помилку й може повторити запит пізніше. Запит завершується не пізніше тайм-ауту БД (2 с; очікування з'єднання обмежене налаштуванням пулу), без часткової відповіді чи змін даних. Після відновлення БД або звільнення з'єднань наступний запит виконується звичайно; ручне втручання не потрібне.

**Застосовані патерни.**

- **Обмеження результатів у БД (`LIMIT`)** — не завантажуються всі збіги, коли сервісу потрібні не більш як 20.
- **Тайм-аут запиту (`statement_timeout`)** — обмежує час виконання пошуку; `SET LOCAL` не залишає налаштування в повторно використаному з'єднанні.
- **Вузький catch і явна помилка** — очікувані збої БД/пулу логуються та перетворюються на `SearchUnavailableError`; дефекти коду проходять назовні.
- **HTTP 503** — клієнт отримує тимчасову помилку, а не хибний успіх.

**Перевірка** (`tests/search/test_postgres.py`):

| Тест | Що перевіряє |
|---|---|
| `test_postgres_search_sets_timeout_and_passes_limit_to_query` | `SET LOCAL statement_timeout = '2s'`, SQL `LIMIT %s` і передавання ліміту параметром |
| `test_postgres_search_translates_only_expected_failures` | `QueryCanceled` і `PoolTimeout` логуються й перетворюються на `SearchUnavailableError` зі збереженням першопричини |
| `test_postgres_search_does_not_translate_unexpected_errors` | Неочікуваний дефект не маскується як тимчасова недоступність |
| `test_postgres_search_matches_titles_paragraphs_and_literal_wildcards` | Інтеграційно перевіряє пошук у назвах та абзацах, буквальні `%` і виключення видалених документів |

### №1, №2, №3. Міграції: відсутня папка, тайм-аути підключення й блокування

#### №1. Відсутня папка міграцій сприймалась як актуальна схема

**Режим відмови.** До виправлення це був мовчазний збій: відсутній каталог давав порожній список міграцій, після чого CLI міг повідомити, що схема актуальна, хоча жодна міграція не була перевірена.

**До** (`src/db/migrate.py`):

```python
files = sorted(directory.glob("*.sql"))
```

**Після.** `migration_files()` кидає `FileNotFoundError`, якщо каталогу немає або він не містить `.sql`. `main()` перевіряє каталог до підключення до БД, виводить причину в `stderr` і повертає код `1`.

**Що бачить користувач.** Замість повідомлення про актуальну схему CLI показує, що каталог міграцій не існує або не містить SQL-файлів. До БД підключення не відбувається, міграції не запускаються.

**Як система відновлюється.** Оператор повертає каталог і потрібні файли міграцій до збірки/розгортання та повторно запускає CLI. Автоматичного повтору немає: це помилка артефакту розгортання, яку потрібно виправити.

#### №2. Підключення до PostgreSQL могло чекати без обмеження часу

**Режим відмови.** До виправлення недоступна або повільна БД могла надовго зависити CLI міграцій, затримуючи розгортання без чіткої помилки.

**До** (підключення без тайм-ауту):

```python
with psycopg.connect(url, autocommit=True) as conn:
    applied = apply_migrations(conn, MIGRATIONS_DIR)
```

**Після.** Підключення має `connect_timeout=10`. Якщо виникає `psycopg.OperationalError`, CLI виводить загальне повідомлення без URL чи пароля та повертає код `2`.

**Що бачить користувач.** Якщо БД не відповідає, команда завершується не пізніше тайм-ауту підключення й повідомляє: «Не вдалося підключитися до бази даних PostgreSQL.» Секрети підключення не потрапляють у повідомлення. Оскільки з'єднання не встановлено, ця спроба не застосовує міграцій.

**Як система відновлюється.** Після відновлення БД або мережевого з'єднання оператор повторно запускає команду. Автоматичних повторів немає; перед повторним запуском не потрібно відновлювати стан міграцій від цієї невдалої спроби.

#### №3. Очікування advisory lock могло бути необмеженим

**Режим відмови.** До виправлення `pg_advisory_lock` міг чекати без обмеження, якщо інший процес утримував lock; CLI і розгортання залишалися заблокованими.

**До**:

```python
conn.execute("SELECT pg_advisory_lock(%s)", (_MIGRATION_LOCK_ID,))
```

**Після.** Перед отриманням lock виконується `SET lock_timeout = '60s'`. Якщо інший процес і далі утримує блокування, PostgreSQL перериває очікування; `main()` виводить «Інший процес уже застосовує міграції» в `stderr` і повертає код `3`.

**Що бачить користувач.** Запуск завершується приблизно після хвилини очікування з повідомленням про інший процес замість нескінченного зависання. Міграції цією невдалою спробою не застосовуються, бо lock потрібен до читання та виконання списку міграцій.

**Як система відновлюється.** Якщо інший процес ще виконує міграції, оператор чекає на його завершення й повторно запускає команду. Якщо lock не звільняється, потрібно перевірити стан процесу, який його утримує; автоматичного повтору немає.

**Перевірка.** `tests/db/test_migrate.py` перевіряє відсутній і порожній каталоги, ранню відмову до підключення, параметр тайм-ауту й відсутність пароля в повідомленні, порядок `SET lock_timeout` перед advisory lock та ненульовий код із повідомленням для зайнятого lock.

### №8. Попередження про сховище в пам'яті

**До.** Якщо `DATABASE_URL` не задано, `create_app()` обирав сховища в пам'яті без попередження. Після перезапуску дані з такого сховища зникають, але користувач не отримував про це явного повідомлення.

**Після.** `create_app()` записує попередження, коли `DATABASE_URL` відсутній і пул не створено:

```python
if database_pool is None and url is None:
    logger.warning(
        "DATABASE_URL не задано: дані зберігаються в памʼяті й "
        "зникнуть після перезапуску"
    )
```

Старт без БД залишається дозволеним: режим зі сховищем у пам'яті потрібен для CI, тестів і локальної розробки. За наявності `DATABASE_URL` це попередження не з'являється.

**Перевірка.** `tests/reliability/test_database_fallback_warning.py` через `caplog` перевіряє обидва випадки: без `DATABASE_URL` попередження є, з ним — немає.
