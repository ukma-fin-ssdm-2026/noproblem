# ADR-003: Архітектурний стиль — клієнт-серверна архітектура з WebSocket

- **Статус:** Прийнято
- **Дата:** 2026-09-30

## Контекст

FR-024–026 вимагають синхронізації змін між співредакторами без конфліктів.

NFR-PERF-006 встановлює вимогу синхронізації змін менш ніж за 1 секунду для до 10 редакторів одночасно.

Тому системі потрібен механізм передачі змін у реальному часі.

## Варіанти

### 1. Клієнт-серверна архітектура з WebSocket

Єдиний серверний процес обслуговує:

- REST API для CRUD-операцій;
- WebSocket-з'єднання для real-time оновлень та блокування абзаців.

### 2. REST-only з polling

Клієнт періодично надсилає запити до сервера для перевірки змін.

Такий підхід простіший у реалізації, але створює затримку між зміною даних та її отриманням клієнтом і не відповідає вимозі швидкої синхронізації.

### 3. Peer-to-peer

Користувачі обмінюються змінами безпосередньо між клієнтами.

Такий підхід ускладнює централізований контроль доступу, оскільки перевірку прав користувачів необхідно виконувати між учасниками системи.

## Рішення

Обрати **клієнт-серверну архітектуру з WebSocket**.

Система використовує:

- REST для CRUD-операцій;
- WebSocket для real-time locking та оновлень;
- PostgreSQL для зберігання даних;
- зовнішній SMTP-сервер для надсилання електронних листів.

REST та WebSocket працюють через спільний шлюз в одному серверному процесі.

## Обґрунтування

Polling створює додаткову затримку між зміною та її доставкою клієнтам, тому він гірше відповідає NFR-PERF-006.

WebSocket дозволяє серверу одразу повідомляти підключених користувачів про зміни та стан блокування абзаців.

Peer-to-peer ускладнює реалізацію централізованого контролю доступу. Для NoteLy це особливо важливо через наявність ролей Owner, Editor та Guest відповідно до FR-040–057.

Клієнт-серверна модель дозволяє централізовано виконувати перевірку прав, керувати блокуваннями та синхронізувати стан документа.

## Наслідки

- Стан активних блокувань абзаців зберігається в пам'яті єдиного серверного процесу.
- Для семестрового проєкту таке обмеження є прийнятним.
- У разі масштабування на декілька серверних інстансів стан блокувань необхідно буде винести у спільне сховище, наприклад Redis.
- Спільний шлюз є єдиною точкою входу до системи, що спрощує аналіз безпеки та контроль доступу.
- Водночас шлюз може стати єдиною точкою відмови, тому в майбутньому може знадобитися додаткове забезпечення відмовостійкості.
- Архітектура безпосередньо підтримує рішення щодо блокування абзаців, прийняте в ADR-001.
