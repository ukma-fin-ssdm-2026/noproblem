# Матриця архітектурної простежуваності

## 1. Призначення

Ця матриця встановлює зв'язок між функціональними та нефункціональними вимогами системи NoteLy, архітектурними компонентами, проєктними рішеннями та способами верифікації.
## 2. Архітектурні компоненти

- **Web Client** — інтерфейс користувача, редактор документа, буфер змін та повтор збереження.
- **Gateway** — точка входу до backend (HTTP/HTTPS та WebSocket/WSS): перевірка токена та обмеження частоти запитів за IP.
- **REST API** — HTTP/HTTPS (JSON) API для основних функцій системи.
- **Collaboration** — WebSocket/WSS-компонент для спільного редагування, автозбереження, знімків версій та управління блокуванням абзаців. Lock Manager є частиною Collaboration, а не окремим архітектурним компонентом.
- **IAM** — реєстрація, автентифікація, сесії, ролі, запрошення, блокування акаунтів та контроль доступу.
- **Documents & Versions** — створення, перейменування, кошик, версії та стан документів.
- **Search** — пошук документів за назвою та вмістом.
- **Calendar & Events** — створення та керування подіями.
- **Scheduler** — фонове очищення кошика після 30 днів.
- **DB** — акаунти, сесії, ролі, документи, версії, події.
- **Email Service** — запрошення та повідомлення для розблокування.

## 6. Сценарії атрибутів якості

### Сценарій 1: Синхронізація змін документа

**«Зміни документа повинні синхронізуватися між співредакторами менш ніж за 1 секунду»**

- **Джерело (вимога):** NFR-PERF-006 (FR-024 – FR-026)
- **Середовище тестування:** staging-середовище з 10 симульованими співредакторами, WebSocket/WSS з'єднання
- **Артефакти:** логи Collaboration, метрики затримки, скріншоти синхронізації у реальному часі, мережеві пакети
- **Сценарій:** користувач A редагує абзац 5; користувач B редагує абзац 7; Collaboration керує блокуванням; обидві зміни передаються клієнтам менш ніж за 1 секунду
- **Очікуваний результат:** обидва користувачі бачать актуальний вміст без конфліктів, затримка < 1 с, блокування дозволяють одному редактору редагувати один абзац одночасно
- **Компоненти:** Collaboration (Lock Manager), Web Client, IAM
- **Тестові випадки:** Test-01, Test-02, Test-03

### Сценарій 2: Контроль доступу до документа

**«Користувач без відповідного дозволу не повинен отримувати доступ до документа»**

- **Джерело (вимога):** NFR-SEC-001 (FR-040 – FR-057)
- **Середовище тестування:** production-like середовище з ролями Owner, Editor, Guest, NoAccess
- **Артефакти:** логи IAM-перевірок, записи REST API 403, логи Collaboration при блокуванні, результати ACL у Search
- **Сценарій:** користувач без дозволу намагається: 1) відкрити документ через REST API, 2) приєднатися до WebSocket у Collaboration, 3) знайти документ через Search; IAM повинна блокувати на кожному кроці
- **Очікуваний результат:** запит повертає 403, документ не відкривається, у логах фіксується відхилення, недоступні документи не в пошуку
- **Компоненти:** IAM, REST API, Collaboration, Documents & Versions, Search
- **Тестові випадки:** Test-07, Test-18, Test-19, Test-20, Test-21, Test-22, Test-23

### Сценарій 3: Надійність при відновленні мережі

**«Раніше збережений вміст документа не повинен втрачатися після відновлення мережи»**

- **Джерело (вимога):** NFR-REL-002 (FR-027 – FR-029)
- **Середовище тестування:** chaos-engineering: симульований обрив мережи на 10 с, втрата пакетів, відновлення
- **Артефакти:** логи буфера Web Client, логи Collaboration, записи DB, результати перевірки цілісності
- **Сценарій:** користувач редагує офлайн (буфер зберігає зміни); мережа відновлюється; Collaboration синхронізує; DB отримує оновлення
- **Очікуваний результат:** усі зміни синхронізуються при повторному з'єднанні, без втрати даних, документ узгоджується
- **Компоненти:** Web Client, Collaboration, Documents & Versions, DB
- **Тестові випадки:** Test-14

## 7. Правило повноти

Матриця повинна підтримувати такі правила:

1. Кожна функціональна вимога має бути пов'язана щонайменше з одним архітектурним компонентом.
2. Кожна нефункціональна вимога має бути пов'язана щонайменше з одним архітектурним компонентом.
3. Кожен компонент архітектури має бути пов'язаний щонайменше з однією вимогою.
4. Для кожної вимоги визначено спосіб її верифікації через конкретні тестові випадки.
5. Зміна вимоги в `docs/requirements/rtm.md` повинна відображатися в цій матриці.
