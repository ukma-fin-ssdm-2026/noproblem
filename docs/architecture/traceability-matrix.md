# Матриця архітектурної простежуваності

## 1. Призначення

Ця матриця встановлює зв'язок між функціональними та нефункціональними вимогами системи NoteLy, архітектурними компонентами, проєктними рішеннями та способами верифікації.
## 2. Архітектурні компоненти
 
- **Web Client** — інтерфейс користувача, редактор документа, буфер змін та повтор збереження
- **Gateway** — точка входу до backend: перевірка токена та обмеження частоти запитів за IP. Роль у документі не перевіряє
- **REST API** — HTTP/JSON API для основних функцій системи
- **Collaboration** — WebSocket-компонент для спільного редагування, автозбереження та знімків версій
- **IAM** — реєстрація, автентифікація, сесії, ролі, запрошення, блокування акаунтів та контроль доступу
- **Documents & Versions** — створення, перейменування, кошик, версії та стан документів
- **Search** — пошук документів за назвою та вмістом
- **Calendar & Events** — створення та керування подіями
- **Scheduler** — фонове очищення кошика після 30 днів
- **DB** — акаунти, сесії, ролі, документи, версії, події
- **Email Service** — запрошення та повідомлення для розблокування

## 6. Сценарії атрибутів якості
 
1. **«Зміни документа повинні синхронізуватися між співредакторами менш ніж за 1 секунду»** → навантажувальний тест (Test-70): 10 одночасних користувачів редагують один документ; критерії успіху — кожна зміна відображається в інших клієнтів < 1 с, без втрати або конфлікту даних.
   - **Вимога:** NFR-PERF-006. **Компоненти:** Collaboration, Web Client, IAM.
2. **«Користувач без відповідного дозволу не повинен отримувати доступ до документа»** → негативний тест безпеки (Test-19, Test-46): створити документ у режимі «Обмежений», авторизувати користувача без доступу, спробувати відкрити документ через інтерфейс, REST API та WebSocket; критерій — у 100% сценаріїв доступ відхиляється, вміст не повертається.
   - **Вимога:** NFR-SEC-001. **Компоненти:** IAM, REST API, Collaboration, Documents & Versions.
3. **«Раніше збережений вміст документа не повинен втрачатися після відновлення мережі»** → хаос-експеримент (Test-74): під час редагування перервати з'єднання, продовжити редагування, відновити з'єднання; критерій — збережений вміст доступний у 100% сценаріїв, нові зміни синхронізуються.
   - **Вимога:** NFR-REL-002. **Компоненти:** Web Client, Collaboration, Documents & Versions.

## 7. Правило повноти

Матриця повинна підтримувати такі правила:

1. Кожна функціональна вимога має бути пов'язана щонайменше з одним архітектурним компонентом.
2. Кожна нефункціональна вимога має бути пов'язана щонайменше з одним архітектурним компонентом.
3. Кожен компонент архітектури має бути пов'язаний щонайменше з однією вимогою.
4. Для кожної вимоги визначено спосіб її верифікації.
5. Зміна вимоги в `docs/requirements/rtm.md` повинна відображатися в цій матриці.
