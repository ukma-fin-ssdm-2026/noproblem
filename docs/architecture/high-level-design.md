# Інтерфейси між компонентами NoteLy

**Архітектурний стиль.** NoteLy побудовано як **модульний моноліт із єдиним шлюзом** (API Gateway) у клієнт-серверній архітектурі. Вебклієнт взаємодіє із системою лише через шлюз: REST/HTTPS для звичайних операцій і WSS для спільного редагування в реальному часі. Серверна частина складається зі слабко зв'язаних модулів із чіткими відповідальностями (ідентичність і доступ, документи та версії, спільне редагування, пошук, календар, планувальник), які розгорнуто в одному серверному процесі та які взаємодіють через внутрішні інтерфейси, а не через мережу. Кожен модуль володіє своїми даними в спільній СУБД PostgreSQL, а єдиним джерелом правди про ролі є модуль IAM, до якого звертаються решта модулів. Такий вибір спрощує розгортання й забезпечує узгодженість даних, а також дозволяє тримати активні блокування абзаців у пам'яті процесу (ADR-003). Чіткі межі модулів залишають можливість у майбутньому виокремити їх у окремі сервіси. Обмін з Email Service є єдиною зовнішньою інтеграцією.

## 1. Призначення та межі опису

Документ описує взаємодію компонентів NoteLy відповідно до компонентної діаграми, вимог системи та прийнятих архітектурних рішень. Він визначає призначення інтерфейсів, напрямок обміну, протокол там, де він заданий, і правила доступу.

Опис є логічним контрактом між компонентами, а не специфікацією конкретних URL, схем JSON або WebSocket-повідомлень. Точні маршрути, назви полів, коди помилок та формат квитка для WebSocket мають бути узгоджені під час проєктування API; джерельні вимоги їх не визначають.

Компонентна діаграма передбачає спільний шлюз у межах одного серверного процесу для REST і WebSocket. Основне сховище — PostgreSQL. Активні блокування абзаців зберігаються в пам'яті серверного процесу відповідно до ADR-003.

## 3. Загальні правила взаємодії

### 3.1 Транспорт і автентифікація

- З'єднання від Web до GW використовує HTTPS для REST та WSS для WebSocket.
- Запити реєстрації, входу та переходу за посиланням-запрошенням є публічними маршрутами. Решта маршрутів потребує токена або квитка, передбаченого для WebSocket-підключення.
- GW перевіряє автентичність токена, застосовує ліміти запитів за IP і передає ідентифікованого користувача далі. GW не вирішує, чи має цей користувач право на конкретний документ або дію.
- IAM є єдиним джерелом правди про ролі `Owner`, `Editor` і `Guest`. Компонент, який виконує операцію над документом або подією, перевіряє потрібне право через IAM.
- Неавторизований запит не повинен повертати захищений вміст документа. Це правило поширюється на REST, WebSocket і результати пошуку.

### 3.2 Помилки та повтори

- Компонент, що виконує операцію, повертає результат або явну помилку; проміжний компонент передає її клієнту без перетворення відмови на успішну відповідь.
- Для некоректних даних клієнт має отримати достатню інформацію для повідомлення про помилку, не втрачаючи введених коректних даних (NFR-USA-001).
- Web зберігає незбережені зміни у буфері та повторює невдале автозбереження кожні 5 секунд до успіху (FR-029).
- Конкретне відображення помилок у HTTP-статусах і WebSocket-кодах закриття цим документом не встановлюється.

## 5. Контракти інтерфейсів

### I-01. Вебклієнт ↔ Шлюз

**REST через HTTPS**

- Web надсилає HTTP-запити для автентифікації, операцій із документами, пошуку, керування доступом і календаря.
- Реєстрація, вхід і прийняття запрошення доступні без чинного токена; інші захищені операції потребують токена.
- GW застосовує ліміти за IP, перевіряє токен на захищених маршрутах і маршрутизує запит до API.
- Операції створення документа мають витримувати повтори клієнта без дублювання документа (FR-012–FR-013); механізм визначається в API-специфікації.

**WebSocket через WSS**

- Web відкриває з'єднання для документа, передаючи токен або передбачений архітектурою квиток.
- Клієнт передає події редактора, позицію курсора та інші дані присутності; отримує оновлення документа, курсори інших учасників, стан блокувань і результат збереження.
- Клієнтський буфер змін зберігається до підтвердження збереження; при помилці клієнт показує повідомлення та повторює спробу.
- Після втрати з'єднання курсор користувача має зникнути в інших учасників не пізніше ніж за 5 секунд (FR-026). Перевірка стану з'єднання в Collab виконується щосекунди згідно з діаграмою.
- Фактичні назви подій, формат повідомлень, механізм видачі/термін дії квитка та правила повторного підключення треба визначити у специфікації WebSocket API.

### I-02. Шлюз → IAM: перевірка токена

- GW передає IAM токен, отриманий із захищеного запиту.
- IAM перевіряє чинність сесії/токена і повертає результат перевірки та ідентифікатор автентифікованого користувача або відмову.
- GW використовує цей результат для автентифікації маршруту; рішення про роль у документі залишається за IAM і компонентом, що виконує операцію.
- Для публічних маршрутів перевірка токена не є передумовою обробки.

### I-03–I-04. Шлюз → REST API та Спільне редагування

- Для HTTP-запиту GW маршрутизує виклик до API; для WSS-з'єднання — до Collab.
- GW передає результат автентифікації та контекст запиту, необхідний для кореляції користувача й операції.
- GW не змінює дані документа та не перевіряє ACL документа.
- Вхід, реєстрація і перехід за посиланням-запрошенням мають бути доступні на публічних маршрутах; після автентифікації запрошений користувач переходить до документа згідно з FR-007.

### I-05. REST API → IAM

API делегує IAM операції, пов'язані з ідентичністю й доступом:

- реєстрацію, вхід, вихід і керування сесіями;
- запрошення користувачів до документа, призначення/зміну ролей, відкликання доступу та зміну режиму доступу;
- створення й обробку запитів на доступ;
- перевірку прав власника перед змінами доступу.

IAM перевіряє вхідні дані та повноваження, змінює акаунти/сесії/ролі й повертає результат або явну відмову. Тільки власник може керувати доступом і режимом доступу документа (FR-040–FR-057). У режимі «За посиланням» IAM під час першого відкриття створює явний запис ролі `Guest`, як зазначено на діаграмі.

### I-06. REST API → Документи та версії

API делегує Docs запити на:

- отримання списку документів і списку кошика;
- створення, перейменування, видалення до кошика та відновлення документа;
- перегляд історії версій і відновлення вибраної версії.

Docs перевіряє права через IAM перед операціями, що стосуються конкретного документа. Документ за замовчуванням має режим доступу «Обмежений»; назва за замовчуванням — «Без назви». Порожня назва та назва понад 100 символів відхиляються. Відновлення з кошика доступне лише власнику. Записи кошика не входять до звичайного пошуку.

### I-07. REST API → Пошук документів

- API передає Search пошуковий запит і контекст користувача.
- Search шукає за назвою та вмістом і повертає збіги з метаданими, потрібними клієнту для відображення результатів.
- Перед поверненням результатів Search застосовує ACL-фільтр через IAM; користувачеві не можна розкривати недоступні документи, зокрема їхні назви.
- Search не включає документи з кошика. Вимога продуктивності: пошук у просторі до 100 документів завершується не довше ніж за 2 секунди (NFR-PERF-005).
- Фільтрація запитів коротших за 2 символи виконується на клієнті згідно з матрицею простежуваності.

### I-08. REST API → Календар і події

API передає Calendar запити на створення, читання, редагування та видалення подій, а також керування учасниками й прив'язками документів.

Calendar забезпечує такі правила:

- назва та час початку є обов'язковими; час завершення не може бути раніше часу початку;
- творець може змінювати й видаляти свою подію та керувати її учасниками;
- учасник, який не є творцем, може вилучити себе, не змінюючи календарі інших учасників;
- додавання документа до події дозволене лише за наявності доступу творця до документа;
- доступ до прив'язаного документа перевіряється також під час читання події; після відкликання доступу прив'язка знімається (FR-063–FR-073).

### I-09. Спільне редагування → IAM

- Під час відкриття документа та перед редагуванням Collab запитує в IAM роль користувача в цьому документі.
- Collab дозволяє редагувати Owner і Editor; Guest має лише право перегляду.
- Collab періодично перевіряє стан з'єднання та актуальність доступу; діаграма встановлює перевірку з'єднання щосекунди.
- Відсутність або відкликання доступу призводить до відмови в доступі до вмісту/редагування, а не до продовження роботи з кешованими правами.

### I-10. Спільне редагування → Документи та версії

- Collab передає Docs зміни вмісту документа та запити на автозбереження не рідше одного разу на 5 секунд активного редагування.
- Collab запитує створення знімків відповідно до правил версій: щонайменше кожні 5 хвилин активного редагування або при зміні автора (FR-030).
- Docs зберігає вміст та версії через DB і повертає результат збереження. Невдалий результат має бути переданий клієнту, щоб Web показав помилку й повторив запит.
- Зміни мають бути видимі співредакторам менш ніж за 1 секунду для до 10 редакторів (NFR-PERF-006).
- Конфлікти редагування одного абзацу запобігаються блокуванням абзацу через Lock Manager відповідно до ADR-001. Lock Manager є частиною модуля Collab.

### I-11. Документи та версії → IAM

Docs запитує в IAM актуальне право користувача перед кожною операцією над документом або версією. Перевірка враховує роль і дію: читання, редагування, перейменування, видалення/відновлення, перегляд історії чи відновлення версії. IAM повертає дозвіл або відмову; Docs не підтримує незалежну копію таблиці ролей.

### I-12. Пошук → IAM

Search передає IAM ідентифікатор користувача та документи-кандидати для перевірки доступу. IAM повертає доступні документи/рішення ACL; Search фільтрує результати до їх повернення через API. Фільтрація є обов'язковою для кожного пошукового запиту (NFR-SEC-002).

### I-13. Календар і події → IAM

Calendar звертається до IAM для:

- перевірки доступу творця до документа під час створення прив'язки та під час читання події;
- перевірки повноважень користувача щодо події та її учасників;
- визначення користувача за email під час додавання учасника.

Calendar зберігає та повертає учасникам лише події, до яких вони мають доступ. Якщо доступ творця до документа відкликано, Calendar знімає прив'язку.

### I-14–I-17. Компоненти → Сховище даних

DB — спільне основне PostgreSQL-сховище; доступ до нього мають серверні компоненти, не браузер. Компоненти звертаються лише до потрібних їм даних:

| Викликач | Дані та правила |
| --- | --- |
| Docs | Документи, абзаци та версії. Операції, що мають зберегти узгоджений стан, виконуються транзакційно. |
| IAM | Акаунти, хеші паролів, невдалі спроби входу, блокування, сесії, ролі та запити на доступ. |
| Search | Дані для пошуку за назвою й вмістом; документи з кошика виключаються. Реалізація може використовувати повнотекстовий пошук PostgreSQL згідно з ADR-002. |
| Calendar | Події, учасники й посилання на документи. Видалення учасника не повинно змінювати участь інших користувачів. |

Схема таблиць і зв'язків визначається окремо в [моделі даних](./data-model.md). ADR-002 передбачає окреме зберігання абзаців; ця деталь узгоджена з поточною ER-моделлю.

### I-18. Планувальник → Документи та версії

- Scheduler періодично знаходить документи, що перебувають у кошику понад 30 днів, і передає Docs команду остаточного видалення (FR-023).
- Docs виконує видалення з урахуванням цілісності даних і каскадного очищення версій, доступів і календарних прив'язок, як зазначено на діаграмі.
- Видалення не виконується для документа, який ще не досяг 30-денного терміну.
- Період запуску планувальника та механізм повтору невдалої задачі мають бути визначені в реалізаційній специфікації; вимоги задають строк зберігання, а не частоту запуску.

### I-19. IAM → Email Service

- IAM викликає Mail для відправлення запрошення до документа та листа з посиланням розблокування після блокування акаунта.
- Адреса одержувача перевіряється, а вміст листа містить лише дані, потрібні для відповідної дії.
- З'єднання з зовнішнім сервісом захищається TLS. Помилка Mail має бути явно оброблена IAM і не повинна маскуватися як успішне надсилання.
- Конкретний SMTP/API-контракт, шаблони листів, строк дії посилань і політика повторних спроб визначаються конфігурацією інтеграції.

## 6. Наскрізні вимоги до інтерфейсів

1. **Контроль доступу:** перевірка токена на GW підтверджує особу, але не замінює перевірку ролі в IAM. Docs, Collab, Search і Calendar не повертають дані без перевірки належного доступу.
2. **Спільне редагування:** WebSocket використовується для змін, курсорів та стану присутності; REST — для звичайних CRUD-операцій. Синхронізація підтримує до 10 редакторів із затримкою менш ніж 1 секунду.
3. **Автозбереження:** активні зміни передаються на збереження не рідше одного разу на 5 секунд; невдале збереження повідомляється користувачу і спроба повторюється.
4. **Узгодженість:** створення документа не повинно залишати неповні або дубльовані записи при повторі чи втраті з'єднання. Відновлення з кошика зберігає назву та вміст.
5. **Безпека каналів:** зовнішні з'єднання використовують HTTPS/WSS; інтеграція з Mail — захищене SMTP/API-з'єднання. Прямий доступ браузера до DB не допускається.
6. **Межі протоколу:** на рівні цього документа визначено HTTPS/WSS та SMTP/API лише там, де це зазначено діаграмою. Формати повідомлень і транспорт внутрішніх викликів не конкретизовані й не повинні вважатися REST/JSON без окремого рішення.
7. **Внутрішні виклики:** компоненти розгорнуті в одному серверному процесі, внутрішні інтерфейси є викликами в межах процесу, а не окремими мережевими сервісами. Це узгоджується з ADR-003.
