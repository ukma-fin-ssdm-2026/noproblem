# Протокол спільного редагування (WebSocket, Collab)

Узгоджено на зустрічі 12.11.2026 (Анастасія Козинська, Оля Марущенко).
Ґрунтується на [ADR-001](decisions/ADR-001-conflict-resolution.md)
(блокування абзацу) і [ADR-003](decisions/ADR-003-architecture-style.md)
(клієнт-сервер + WebSocket).

Змінювати протокол лише за домовленістю всієї команди: від нього залежать
бекенд (`src/collab/`) і фронтенд.

**Коротко.** WebSocket лише розсилає зміни й тримає блокування. Текст
абзаців фронтенд читає і зберігає через REST, як і раніше
(`GET` / `PATCH /api/v1/documents/{id}/paragraphs/{pid}`). Так дані в базі
завжди проходять через один шлях і одні перевірки.

## 1. Ендпоінт і авторизація

- Адреса: `WS /api/v1/collab/documents/{document_id}`
  (локально `ws://localhost:3000/...`, на Render `wss://...`).
- Перше повідомлення клієнта — `{"type": "auth", "token": "<токен сесії>"}`,
  не пізніше ніж через **5 с** після підключення. Токен не передаємо в URL
  (потрапляє в логи) і не в заголовку (браузерний `WebSocket` не вміє ставити
  `Authorization`).
- Токен перевіряє `AuthService.verify_session`, як і в REST
  (`src/api/security.py`). Доступ до документа — право `VIEW`; щоб заблокувати
  абзац, потрібне право `EDIT` (Owner або Editor).

## 2. Коди закриття з'єднання

| Код    | Коли                                                     |
|--------|----------------------------------------------------------|
| `4401` | За 5 с не прийшло `auth`, або токен недійсний            |
| `4403` | Немає доступу до документа (або документа не існує); доступ відкликано під час роботи |
| `4404` | Документ у кошику; документ перемістили в кошик під час роботи |
| `4408` | 5 с від клієнта не було жодного повідомлення (heartbeat) |
| `1000` | Звичайне закриття                                        |

Коди 4000–4999 зарезервовані для застосунків; останні три цифри збігаються з
HTTP-кодами. Як і в REST, для неіснуючого документа повертаємо `4403`, а не
`4404`: так перебором номерів не можна дізнатися, які документи існують.

## 3. Повідомлення

Кожне повідомлення — JSON-об'єкт із полем `type`. Ідентифікатори
користувачів — рядки UUID, абзаців — цілі числа.

| Напрям          | `type`              | Поля                                                                 | Що означає |
|-----------------|---------------------|----------------------------------------------------------------------|------------|
| клієнт → сервер | `auth`              | `token`                                                              | Перше повідомлення |
| сервер → клієнту| `welcome`           | `user_id`, `role` (`owner`/`editor`/`guest`), `users` (список `{user_id, name}`), `locks` (`{paragraph_id: user_id}`) | Стан документа на момент входу |
| клієнт → сервер | `ping`              | —                                                                    | Heartbeat раз на 2 с |
| сервер → клієнту| `pong`              | —                                                                    | Відповідь на `ping` |
| клієнт → сервер | `lock.acquire`      | `paragraph_id`                                                       | Хочу редагувати абзац |
| сервер → клієнту| `lock.granted`      | `paragraph_id`                                                       | Абзац твій |
| сервер → клієнту| `lock.denied`       | `paragraph_id`, `holder` (`user_id` або `null`), `reason`: `locked` / `forbidden` | Абзац редагує інший або в тебе роль Guest |
| сервер → усім   | `lock.changed`      | `paragraph_id`, `user_id` або `null`                                 | Хтось узяв або відпустив абзац |
| клієнт → сервер | `paragraph.edit`    | `paragraph_id`, `content`                                            | Повний текст абзацу (не різниця), до 10 000 символів. Лише від власника блокування; не частіше ніж раз на 200 мс |
| сервер → іншим  | `paragraph.updated` | `paragraph_id`, `content`, `author_id`                               | Розсилка зміни всім, крім з'єднання автора |
| клієнт → сервер | `lock.release`      | `paragraph_id`                                                       | Закінчила редагувати |
| сервер → усім   | `presence`          | `user_id`, `name`, `status`: `joined` / `left`                       | Хтось відкрив або закрив документ |
| сервер → усім   | `document.changed`  | `kind`: `paragraphs` / `title` / `trashed`, `author_id`              | Документ змінено через REST; дані перечитати через REST (розділ 7) |
| клієнт → сервер | `cursor`            | `paragraph_id` (або `null`), `offset`                                | Де мій курсор; не частіше ніж раз на 100 мс (розділ 8) |
| сервер → іншим  | `cursor`            | `user_id`, `paragraph_id` (або `null`), `offset`                     | Де курсор іншого співредактора |
| сервер → клієнту| `error`             | `code`, `message`                                                    | `invalid_message`, `lock_required`, `too_long`, `forbidden`; `message` українською |

Некоректний JSON, невідомий `type` або поле не того типу дають `error` з
`invalid_message`; з'єднання при цьому не рветься.

`paragraph.updated` не надходить лише тому з'єднанню, з якого прийшла зміна.
Друга вкладка того самого користувача його отримує.

## 4. Правила блокувань

- У абзацу щонайбільше один власник. Повторний `lock.acquire` тим самим
  користувачем → `lock.granted` (без помилки).
- Один користувач може тримати кілька абзаців; фронтенд відпускає абзац,
  коли з нього йде фокус.
- Блокування знімається при `lock.release`, при закритті з'єднання і при
  тайм-ауті heartbeat. Іншого тайм-ауту бездіяльності немає (ADR-001).
- `lock.release` чужого блокування нічого не робить.
- Guest отримує `lock.denied` з `reason: "forbidden"` (I-09).
- Блокування належать користувачу, а не з'єднанню. Якщо документ відкрито в
  двох вкладках, блокування знімаються й `presence: left` розсилається лише
  тоді, коли закрито останнє з'єднання цього користувача.
- REST поважає блокування: `PATCH` і `DELETE` абзацу, який тримає інший
  користувач, повертають `409`. Вільний абзац можна змінювати без блокування.

## 5. Heartbeat

Клієнт надсилає `ping` раз на 2 с, сервер відповідає `pong`. Якщо 5 с від
клієнта не було жодного повідомлення, сервер закриває з'єднання з кодом
`4408`, знімає блокування і розсилає `presence: left` (FR-026).

## 6. Що робить фронтенд

1. Відкрити WebSocket, одразу надіслати `auth`, дочекатися `welcome`.
   Позначити абзаци з `locks` як зайняті, показати `users`.
2. Фокус в абзаці → `lock.acquire`. Поки не прийшло `lock.granted`, абзац
   лише для читання. `lock.denied` → показати, хто редагує.
3. Під час введення → `paragraph.edit` не частіше ніж раз на 200 мс і, як
   зараз, `PATCH` через `document-save-queue.js`.
4. Фокус зник → `lock.release`.
5. `paragraph.updated` → замінити текст абзацу; `lock.changed` і `presence`
   → оновити позначки.
6. `ping` раз на 2 с. Після закриття з кодом, відмінним від
   `4401`/`4403`/`4404`, — перепідключитися (після перезапуску сервера
   блокування скидаються).
7. `409` від REST → абзац редагує інший користувач: показати повідомлення,
   не повторювати запит.
8. `document.changed` → перечитати через REST те, що змінилося
   (розділ 7). Кілька повідомлень підряд склеювати: перечитувати не частіше
   ніж раз на 300 мс.
9. Курсор змінив місце → `cursor` не частіше ніж раз на 100 мс;
   фокус зник → `cursor` з `paragraph_id: null`. Чужий `cursor` → показати
   мітку; `presence: left` → прибрати мітку цього користувача (розділ 8).

## 7. Зміни поза WebSocket

Частина змін іде через REST, і сервер повідомляє про них усіх у документі,
включно з автором: REST не знає, з якої вкладки прийшов запит, а друга
вкладка автора теж має оновитися.

**Структура документа.** Повідомлення `document.changed` не містить даних:
клієнт перечитує їх через REST. Так джерело правди одне, і повідомлення,
що обігнали одне одне, не зіб'ють порядок абзаців.

| `kind`       | Коли                                                   | Що робить фронтенд |
|--------------|--------------------------------------------------------|--------------------|
| `paragraphs` | Абзац додано, видалено або переміщено                  | Перечитати `GET /documents/{id}/paragraphs`; прибрати позначки блокувань з абзаців, яких уже немає |
| `title`      | Документ перейменовано                                 | Перечитати `GET /documents/{id}` |
| `trashed`    | Документ перемістили в кошик                           | Нічого: одразу після цього сервер закриває з'єднання з кодом `4404` |

Окремого `lock.changed` після видалення абзацу через REST немає: його
закриває перечитування абзаців.

**Зміна доступу.** Щойно власник змінив чи забрав роль, сервер перевіряє
права цього користувача заново, не чекаючи його наступного повідомлення:

- немає права `VIEW` → усі його з'єднання з документом закриваються з кодом
  `4403`, блокування знімаються, іншим — `lock.changed` і `presence: left`;
- є `VIEW`, але немає `EDIT` (Editor став Guest) → його блокування
  знімаються, усім — `lock.changed`; з'єднання лишається.

Перевірка прав при кожному `lock.acquire` лишається як друга лінія захисту.

## 8. Курсори

Позиція курсора співредакторів (FR-025): абзац і зміщення в ньому. Сервер
нічого не зберігає, лише пересилає іншим.

- `cursor` надсилають лише Owner і Editor; від Guest — `error` з кодом
  `forbidden`.
- `offset` — ціле число від 0 до 10 000; `paragraph_id` — номер абзацу або
  `null`, коли фокус пішов з тексту. Інакше — `invalid_message`.
- Клієнт надсилає не частіше ніж раз на 100 мс; сервер цього не перевіряє.
- Курсор зникає разом із `presence: left`, тобто щонайпізніше за 5 с після
  втрати з'єднання (FR-026, через heartbeat).
- Новий учасник не бачить чужих курсорів, доки вони не зрушать: у `welcome`
  курсорів немає.
- Після чужого `paragraph.updated` мітки в цьому абзаці можуть стати не
  на місце; найпростіше — ховати їх до наступного `cursor`.

## Приклад

```text
→ {"type": "auth", "token": "..."}
← {"type": "welcome", "user_id": "a1...", "role": "editor",
   "users": [{"user_id": "a1...", "name": "Олена"}], "locks": {}}
→ {"type": "lock.acquire", "paragraph_id": 7}
← {"type": "lock.granted", "paragraph_id": 7}
← {"type": "lock.changed", "paragraph_id": 7, "user_id": "a1..."}
→ {"type": "paragraph.edit", "paragraph_id": 7, "content": "Новий текст"}
→ {"type": "lock.release", "paragraph_id": 7}
← {"type": "lock.changed", "paragraph_id": 7, "user_id": null}
```

Зміни через REST і курсори:

```text
→ {"type": "cursor", "paragraph_id": 7, "offset": 12}
   (іншим) {"type": "cursor", "user_id": "a1...", "paragraph_id": 7, "offset": 12}
   (хтось додав абзац через REST)
← {"type": "document.changed", "kind": "paragraphs", "author_id": "b2..."}
→ GET /api/v1/documents/1/paragraphs
```
