# Проєктування API NoteLy

## Огляд архітектури

| Властивість | Рішення |
| --- | --- |
| Стиль | REST поверх HTTP для звичайних операцій; JSON у запитах і відповідях |
| Базовий шлях | `http://localhost:3000/api/v1` для локального запуску, налаштованого в README |
| Версія | `v1`, закодована в шляху URL (`/api/v1`) |
| Інтерфейс документації | Swagger UI за адресою `http://localhost:3000/api-docs`; OpenAPI генерується з FastAPI |
| Автентифікація | Непрозорі (opaque) Bearer-токени сесій модуля IAM (`Authorization: Bearer <токен>`), реалізовано в `/auth`. Маршрути документів поки не захищені |
| Зберігання | Поточна заглушка тримає документи й абзаци в пам'яті процесу; дані скидаються після перезапуску. Цільова архітектура передбачає PostgreSQL |
| Спільне редагування | За архітектурою — WebSocket/WSS; у поточному `main.py` WebSocket-маршрутів немає |

Ця документація розрізняє контракт наявної реалізації та функції, що випливають із вимог і архітектури, але ще не представлені в `main.py`. Тому перелік маршрутів нижче описує саме реалізований демонстраційний API, а не повний API продукту.

## Модель ресурсів

### Документ (`Document`)

Основний ресурс робочого простору. Один документ може містити багато абзаців; у цільовій моделі він належить користувачу-власнику й може мати кілька записів доступу, запитів на доступ, версій і прив'язок до подій.

| Атрибут | Тип | Значення |
| --- | --- | --- |
| `id` | integer | Унікальний додатний ідентифікатор |
| `title` | string | Назва; до 100 символів |
| `access_mode` | enum | `restricted` або `link`; нові документи створюються з `restricted` |
| `created_at` | datetime | Час створення в UTC |
| `updated_at` | datetime | Час останньої зміни в UTC |
| `deleted_at` | datetime \| null | Час переміщення до кошика; `null` для активного документа |

Якщо назву не передати під час створення, використовується `Без назви`. Видалення документа є м'яким: ресурс переходить до кошика й може бути відновлений. API повертає окремі списки активних документів і документів кошика.

### Абзац (`Paragraph`)

Абзац є вкладеним ресурсом документа: документ містить упорядкований список абзаців, а кожен абзац належить одному документу.

| Атрибут | Тип | Значення |
| --- | --- | --- |
| `id` | integer | Унікальний додатний ідентифікатор |
| `document_id` | integer | Ідентифікатор документа-власника |
| `position` | integer | Нульова позиція у документі |
| `content` | string | Текст абзацу; порожній текст дозволений |

Створення може додати абзац у кінець або вставити його за `position`. Часткове оновлення змінює `content`, `position` або обидва поля. Після вставлення, переміщення чи видалення позиції абзаців нормалізуються.

### Інші доменні ресурси цільової системи

Модель даних NoteLy також визначає `User`, `DocumentAccess`, `AccessRequest`, `DocumentVersion`, `CalendarEvent` та `EventParticipant`. Користувачі та сесії обслуговуються маршрутами `/auth` (розділ «Автентифікація» нижче). Керування доступом, історія версій, пошук, календар і керування учасниками поки залишаються поза поточним набором маршрутів.

## Кінцеві точки v1

У таблиці шляхи наведені відносно базового шляху `/api/v1`. Усі успішні відповіді з тілом мають формат JSON; відповіді `204` тіла не містять. Ідентифікатори в шляхах мають бути додатними цілими числами.

| Метод і шлях | Призначення | Успіх | Помилки, визначені контрактом |
| --- | --- | --- | --- |
| `POST /documents` | Створити документ; потрібен заголовок `Idempotency-Key` | `201` | `409`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `GET /documents` | Сторінка активних документів | `200` | `422`; `401`/`403` описані лише як інтеграційний контракт |
| `GET /documents/trash` | Сторінка документів у кошику | `200` | `422`; `401`/`403` описані лише як інтеграційний контракт |
| `GET /documents/{document_id}` | Отримати активний документ | `200` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `PUT /documents/{document_id}` | Перейменувати активний документ | `200` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `DELETE /documents/{document_id}` | Перемістити активний документ до кошика | `204` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `POST /documents/{document_id}/restore` | Відновити документ із кошика | `200` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `GET /documents/{document_id}/paragraphs` | Отримати абзаци активного документа | `200` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `POST /documents/{document_id}/paragraphs` | Створити абзац | `201` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `GET /documents/{document_id}/paragraphs/{paragraph_id}` | Отримати абзац | `200` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `PATCH /documents/{document_id}/paragraphs/{paragraph_id}` | Частково оновити абзац | `200` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |
| `DELETE /documents/{document_id}/paragraphs/{paragraph_id}` | Видалити абзац | `204` | `404`, `422`; `401`/`403` описані лише як інтеграційний контракт |

### Автентифікація (`/auth`, модуль IAM)

| Метод і шлях | Призначення | Успіх | Помилки |
| --- | --- | --- | --- |
| `POST /auth/register` | Реєстрація та перша сесія (FR-001, FR-002) | `201` | `409` email зайнятий, `422` з конкретною причиною |
| `POST /auth/login` | Вхід (FR-003–FR-005) | `200` | `401` «Невірний email або пароль», `423` блокування + `Retry-After`, `422` |
| `POST /auth/logout` | Вихід, токен недійсний одразу (FR-006) | `204` | `401` |
| `GET /auth/me` | Власник токена (I-02) | `200` | `401` |
| `POST /auth/unlock` | Розблокування за токеном із листа (FR-005) | `204` | `400`, `422` |

**Чому непрозорі токени, а не JWT.** JWT неможливо відкликати до кінця строку дії без додаткового «чорного списку» на сервері, тому чистий JWT не виконує FR-006 (інвалідація протягом 1 с). Непрозорий токен — 256 випадкових біт (`secrets.token_urlsafe(32)`). Сервер зберігає лише його SHA-256 відбиток, і вихід просто видаляє запис. Сесія завершується через 30 хвилин бездіяльності або через 12 годин від входу (два таймаути за OWASP). Паролі хешуються Argon2id.

Порядок перевірок для захищених маршрутів: спершу автентифікація (401), потім валідація тіла (422).

### Параметри й ідемпотентність

- Списки документів і кошика підтримують `limit` (за замовчуванням `20`, допустимий діапазон `1–100`) та `offset` (за замовчуванням `0`, значення не менше нуля).
- Відповідь списку має форму `{ "documents": [...], "pagination": { "limit", "offset", "total", "has_more" } }`. `has_more` дорівнює `true`, якщо після поточної сторінки лишаються елементи.
- `POST /documents` вимагає заголовок `Idempotency-Key` довжиною від 1 до 128 символів. Повтор того самого ключа з тією самою назвою повертає той самий ресурс зі статусом `201`; повторне використання ключа з іншою назвою повертає `409 Conflict`.
- Назва при створенні необов'язкова; при оновленні обов'язкова, після обрізання пробілів має містити від 1 до 100 символів.
- `PATCH` абзацу має містити щонайменше одне з полів `content` або `position`; позиції повинні залишатися в межах наявного списку.

## Статус-коди та помилки

| Код | Значення в API |
| --- | --- |
| `200 OK` | Успішне читання, перейменування або відновлення ресурсу |
| `201 Created` | Документ або абзац створено; для повтору ідемпотентного створення документа повертається той самий статус |
| `204 No Content` | Документ переміщено до кошика або абзац видалено; тіло відповіді відсутнє |
| `401 Unauthorized` | Відсутній або недійсний токен; для `/auth/login` — невірна пара email/пароль. Для маршрутів документів поки лише контракт |
| `403 Forbidden` | У цільовому контракті — автентифікованому користувачу бракує прав. У поточній заглушці перевірка прав не виконується |
| `404 Not Found` | Документ/абзац не існує, документ не активний або його немає в кошику |
| `409 Conflict` | Ключ ідемпотентності повторно використаний з іншою назвою документа; email уже зареєстрований |
| `423 Locked` | Вхід тимчасово заблоковано після 5 невдалих спроб (FR-005) |
| `400 Bad Request` | Недійсне або застаріле посилання розблокування |
| `422 Unprocessable Entity` | Невалідні параметри шляху, запиту, заголовка або тіла, зокрема позиція абзацу поза допустимими межами |

Відповіді з помилками мають форму `{ "detail": "..." }`. Для помилок валідації реалізація повертає узагальнене повідомлення `Некоректні вхідні дані.` без деталізації помилок за полями; машинозчитуваного коду помилки наразі немає. Відповіді `401` і `403` присутні у згенерованій OpenAPI-специфікації як майбутній інтеграційний контракт, але не генеруються реальною автентифікацією чи авторизацією в `main.py`.

## Версіонування

Версія API задається префіксом шляху: `/api/v1`. Несумісні зміни контракту мають виходити в новій версії шляху (наприклад, `/api/v2`), не змінюючи поведінку клієнтів v1. Сумісні доповнення можна додавати в межах поточної версії, зберігаючи наявні поля, значення та семантику статус-кодів. Політика строків підтримки й виведення старих версій наразі не визначена.

## Проєктні рішення

### Code-First та OpenAPI

Контракт реалізований моделями Pydantic, параметрами FastAPI та метаданими маршрутів у `src/api/main.py`. Специфікація `docs/api/openapi-generated.yaml` генерується з фактичного застосунку автоматично під час запуску сервера (через `lifespan`, функція `export_openapi`); шлях можна змінити змінною оточення `OPENAPI_PATH`. Скрипт `scripts/generate_openapi.py` лишається для CI і використовує ту саму функцію, тому обидва способи дають однаковий YAML. Якщо файлова система доступна лише для читання, запис пропускається без зупинки сервера. Цей документ описує контракт і межі реалізації; при зміні маршрутів його потрібно оновлювати разом із кодом.

Після push у `main` зі змінами в шляхах, визначених у `.github/workflows/deploy-api-docs.yml`, GitHub Actions запускає цей самий скрипт, перевіряє, що закомічена специфікація відповідає коду, та публікує документацію. Workflow не комітить згенерований файл назад у репозиторій: після зміни контракту потрібно згенерувати й закомітити YAML, інакше перевірка CI завершиться помилкою. Якщо запис неможливий під час запуску сервера, з'являється попередження, але сервер продовжує запуск; у скрипті для CI така помилка завершується ненульовим кодом.

### Пагінація

Для списків використовується offset-пагінація: вона проста для клієнтського інтерфейсу та відповідає невеликому очікуваному обсягу даних. Ліміт за замовчуванням — 20, верхня межа — 100; відповідь містить `total` і `has_more`.

### Сумісність вимог і реалізації

Порівняння маршрутів `src/api/main.py` з контрактом вище та таблицею кінцевих точок у `docs/api/validation-report.md`:

| Перевірка | Результат |
| --- | --- |
| Базовий префікс `/api/v1` і перелік із 12 HTTP-маршрутів | Збігаються |
| Методи, параметри списків і тіла запитів | Збігаються з реалізованими моделями та параметрами FastAPI |
| Успішні коди `200`, `201`, `204`, а також `404`, `409`, `422` | Збігаються з поведінкою маршрутів і валідацією |
| `401`/`403` у OpenAPI | Документовані, але не виконуються кодом; автентифікація й перевірка ролей ще не реалізовані |
| Формат помилок | Для відомих помилок використовується `detail`; валідація повертає лише загальне повідомлення, а не помилки окремих полів |
| Повнота щодо цільової архітектури | Часткова: API охоплює документи та абзаци, але не акаунти, права доступу, версії, пошук, календар і WebSocket |
| Сховище | Реалізація зберігає стан лише в пам'яті, тоді як архітектура передбачає PostgreSQL |

Отже, реалізовані кінцеві точки відповідають цьому опису v1. Відповідність до повного набору системних вимог є частковою; описані вище обмеження не слід трактувати як уже реалізовані можливості.
