# Атрибути якості системи NoteLy API

**Наявні засоби та межі вимірювання:**
- Застосунок експонує `/metrics`: `http_requests_total` (мітки `method`, `route`, `status`), `http_request_duration_seconds` (histogram з межею 150 мс), `http_response_size_bytes` і `idempotent_replays_total` (без міток `outcome`). Налаштування Prometheus і панель Grafana є в репозиторії.
- Навантажувальний сценарій Locust є в `loadtests/locustfile.py`; він перевіряє читання, створення та повтор створення документів. Запуск сам по собі не є доказом досягнення цілі, якщо не зафіксовані параметри та результат.
- Функціональні перевірки pytest є в `tests/`. У таблицях нижче виміряне означає, що в репозиторії є відповідний тест або артефакт; заплановане/не виміряне чітко позначено.

## 1. Продуктивність

### 1.1 Час відповіді API

| Параметр | Значення |
|----------|----------|
| **Ціль** | p95 < 150 мс на операції читання (список документів, отримання документа, список абзаців) |
| **Умова провалу** | p95 ≥ 150 мс при навантаженні 10+ одночасних користувачів протягом 5-хвилинного тесту |
| **Реалізація** | Документи й абзаци зберігаються в пам'яті процесу (`dict`); списки документів/абзаців сортуються перед відповіддю. Це прототип, не production-сховище. |
| **Вимірювання** | Prometheus histogram `http_request_duration_seconds` та Locust сценарій є в репозиторії. Збережений Locust-звіт показує загальний p95 13 мс (`loadtests/last_run.json`), але не містить параметрів навантаження, тому не підтверджує ціль для 10+ користувачів протягом 5 хв. |

### 1.2 Пропускна спроможність

| Параметр | Значення |
|----------|----------|
| **Ціль** | ≥ 500 запитів/с на одному вузлі API, при цьому p95 < 150 мс |
| **Умова провалу** | Пропускна здатність < 500 запитів/с АБО p95 ≥ 150 мс при цьому навантаженні |
| **Реалізація** | Документи зберігаються в пам'яті, БД немає. `limit` обмежений значенням 100 (за замовчуванням 20), `offset` — від 0 (за замовчуванням 0); клієнту не обов'язково передавати параметри пагінації. |
| **Вимірювання** | У збереженому `loadtests/out_stats.csv` aggregate зафіксовано **20,58 запитів/с** (598 запитів). Це довідкове baseline-значення з артефакту без зафіксованого середовища/параметрів CI, а не гарантія порівнюваності. Воно нижче цілі 500 запитів/с; ціль не підтверджена. Locust-сценарій доступний у `loadtests/locustfile.py`. |

### 1.3 Розмір відповіді при пагінації

| Параметр | Значення |
|----------|----------|
| **Ціль** | Розмір відповіді зі списком < 500 КБ при `limit=100` |
| **Умова провалу** | Будь-яка сторінка > 500 КБ АБО список повертається без обмеження `limit` |
| **Реалізація** | Заглушка повертає `DocumentsResponse` із метаданими пагінації; `limit` не перевищує 100, назва документа обмежена 100 символами. |
| **Вимірювання** | Histogram `http_response_size_bytes` вимірює Content-Length; `tests/api/test_documents_boundaries.py::test_pagination_limit_at_boundary_is_accepted` перевіряє межу кількості елементів, але не байтовий розмір. Окремого тесту розміру сторінки зі 100 документів у репозиторії немає, тому ціль не підтверджена. |

## 2. Безпека

### 2.1 Валідація вхідних даних

| Параметр | Значення |
|----------|----------|
| **Ціль** | 100% запитів із невалідним тілом, параметрами чи заголовками отримують 422 (помилка схеми) або 400 (семантична помилка) |
| **Умова провалу** | Невалідний запит отримує 2xx або 5xx. Коди 401/403/404 допустимі лише якщо автентифікація, авторизація чи пошук ресурсу відбуваються раніше за валідацію (порядок перевірок задокументований). |
| **Реалізація** | Pydantic-валідація на всіх endpoint'ах: `DocumentCreate` (мін./макс. довжина title), `ParagraphCreate` (position ≥ 0), `ParagraphUpdate` (потрібне хоча б одне поле). Обробник `RequestValidationError` повертає 422. |
| **Вимірювання** | Наявні перевірки меж: `tests/api/test_documents_boundaries.py::test_title_over_100_characters_is_rejected`, `::test_missing_idempotency_key_is_rejected`, `tests/api/test_paragraphs.py::test_patch_without_changes_is_rejected` та інші. Вони покривають конкретні випадки, не доводять валідацію для будь-якого входу. Окремої метрики `validation_errors_total` немає. |

### 2.2 Контракт автентифікації

| Параметр | Значення |
|----------|----------|
| **Ціль** | 100% захищених операцій вимагають дійсний Bearer-токен сесії; OpenAPI позначає захищені операції security scheme. |
| **Умова провалу** | Будь-який захищений запит без/з недійсним токеном не повертає 401, або хоча б одна захищена операція не позначена security scheme. |
| **Реалізація** | Автентифікація через IAM реалізована: `HTTPBearer` і `require_user` перевіряють токен сесії; дозволи на документ перевіряються окремо. Security scheme генерується FastAPI з залежностей маршрутів. |
| **Вимірювання** | Наявні `tests/api/test_auth_api.py::TestIntegrationWithExistingApi::test_document_routes_require_token`, `::test_openapi_marks_protected_routes` та `tests/api/test_documents_api.py::test_without_token_documents_are_closed`. OpenAPI-тест перевіряє конкретні захищені операції, а не довільну повноту всього API. |

## 3. Надійність

### 3.1 Збереження даних

Ця вимога розділена на дві гарантії: прототип забезпечує читання запису в межах процесу, але не довговічність після його перезапуску.

| Параметр | 3.1а. Узгодженість «запис → читання» | 3.1б. Довговічність при крахові процесу |
|----------|----------|----------|
| **Ціль** | 100% успішних записів читаються наступним запитом у тому самому процесі; запис < 10 мс | 100% підтверджених записів доступні після щонайменше 1 перезапуску процесу |
| **Умова провалу** | Успішний статус, але наступне читання не знаходить дані АБО запис > 10 мс | Після перезапуску дані, підтверджені клієнту, відсутні |
| **Реалізація** | Запис у dict виконується синхронно до `return`. | Заглушка зберігає дані лише в пам'яті. Production: PostgreSQL із синхронним комітом. |
| **Вимірювання** | Перевірки створення/читання є в `tests/api/test_documents_api.py::test_prototype_story` та `tests/api/test_document_lifecycle.py::test_owner_reads_own_document`; інваріанти абзаців перевіряються в `tests/api/test_paragraphs.py`. Ці тести не вимірюють час запису. | Заглушка зберігає дані лише в пам'яті; після перезапуску вони втрачаються. Перевірки збереження після рестарту або production-БД у репозиторії немає; ціль не виконується. |

### 3.2 Ідемпотентність операцій запису

| Параметр | Значення |
|----------|----------|
| **Ціль** | 100% повторів `POST /documents` з тим самим обов'язковим `Idempotency-Key` (1–128 символів) і назвою, поки запис ключа зберігається в пам'яті, повертають той самий документ зі статусом 201 без дубліката; зміна назви з тим самим ключем дає 409. |
| **Умова провалу** | Будь-який повтор створює дублікат/повертає інший документ, або повтор із іншою назвою не дає 409. |
| **Реалізація** | `create_document()` зберігає `(title, DocumentResponse)` у пам'яті за ключем `(user.id, Idempotency-Key)`. Заголовок обов'язковий; TTL для ключа не реалізовано. Записи губляться після перезапуску. |
| **Вимірювання** | Наявні `tests/api/test_documents_boundaries.py::test_replay_with_same_title_returns_original_document`, `::test_replay_with_different_title_is_conflict`, `::test_missing_idempotency_key_is_rejected`; `idempotent_replays_total` рахує успішні повтори й не має мітки `outcome`. |

### 3.3 Контракт обробки помилок

| Параметр | Значення |
|----------|----------|
| **Ціль** | 100% передбачених клієнтських помилок (400/401/403/404/409/422/423) повертають відповідний статус і тіло `{"detail": ...}`; неочікувані винятки не маскуються як успішна відповідь. |
| **Умова провалу** | Будь-яка передбачена клієнтська помилка повертає 2xx/5xx або тіло без `detail`. |
| **Реалізація** | Передбачені помилки повертаються через `HTTPException` або явний IAM error handler; `RequestValidationError` перетворюється на 422 із загальним `detail`. Загального обробника 500, UUID кореляції чи спеціального логування stack trace у цьому API немає. |
| **Вимірювання** | Конкретні статуси перевіряють API-тести для валідації, відсутніх ресурсів і конфлікту, зокрема `tests/api/test_documents_boundaries.py::test_replay_with_different_title_is_conflict` та `tests/api/test_paragraphs.py::test_patch_without_changes_is_rejected`. Окремого тесту 500/UUID немає. |

### 3.4 Цілісність даних при конкурентному доступі

| Параметр | Значення |
|----------|----------|
| **Ціль** | Після щонайменше 5 одночасних змін одного документа позиції всіх абзаців лишаються неперервними, без пропусків і дублів; конфліктна зміна має завершитися явним 409, а не тихою втратою. |
| **Умова провалу** | Після серії конкурентних PATCH позиції мають пропуски (1,2,4) або дублі (1,2,2,3) АБО зміна втрачена без відповіді 409 |
| **Реалізація** | Абзаци змінюються в пам'яті; версій документа, блокування чи обробки конкурентного конфлікту через 409 немає. |
| **Вимірювання** | `tests/api/test_paragraphs.py::test_insert_at_valid_position`, `::test_move_paragraph` і `::test_delete_renumbers_remaining` перевіряють послідовність позицій послідовно. Навантажувального тесту конкурентного редагування в репозиторії немає; ціль не підтверджена. |

## 4. Доступність

### 4.1 Доступність API

| Параметр | Значення |
|----------|----------|
| **Ціль** | Частка успішних запитів (не 5xx) ≥ 99,9% за 30 днів (production) |
| **Умова провалу** | Частка 5xx > 0,1% у 30-денному вікні АБО витрачено весь бюджет помилок (≈ 43 хв простою на 30 днів) |
| **Реалізація** | У репозиторії є один застосунок без резервування/балансувальника. HTTP middleware збирає лічильник запитів зі статусом; конфігурації production-інстансів тут немає. |
| **Вимірювання** | Prometheus-метрика `http_requests_total{status=...}` та dashboard Grafana наявні; 30-денного production-вимірювання або налаштованого алерта на 0,1% помилок у репозиторії немає. Ціль не підтверджена. |

## 5. Матриця атрибутів якості та компромісів

### 5.1 Таблиця компромісів (Trade-off Matrix)

| Атрибут 1 ↔ Атрибут 2 | Характер компромісу | Вплив на систему | Обраний пріоритет | Пом'якшення |
|---|---|---|---|---|
| **Надійність ↔ Продуктивність** | Синхронне оновлення пам'яті дає швидку відповідь, але не переживає перезапуск; довговічне сховище вимагає окремого вимірювання затримки | Високий вплив на надійність прототипу; вплив на швидкість сховища не виміряно | Надійність > Продуктивність | Наразі компроміс не усунуто: у репозиторії немає постійного сховища. |
| **Безпека ↔ Продуктивність** | Автентифікація, авторизація та Pydantic-валідація виконуються на запитах | Вартість не виміряна окремо; загальна затримка збирається | Безпека > Продуктивність | Не послаблювати перевірки; вимірювати за `http_request_duration_seconds`. |
| **Надійність ↔ Масштабованість** | Документи й абзаци зберігаються в пам'яті одного процесу; стан губиться після рестарту | Високий вплив; масштабування між процесами не перевірено | Надійність у production | Постійне сховище та багатопроцесний режим — не реалізовані в цьому репозиторії. |
| **Продуктивність ↔ Функціональність** | Пагінація списку `limit ≤ 100`: для колекції з понад 100 документів потрібно кілька запитів | LOW | Продуктивність > Функціональність | Можна розглянути інше максимальне значення після вимірювання 1.1 та 1.3; збільшення ліміту не реалізоване. |
| **Надійність ↔ Зручність** | `Idempotency-Key` обов'язковий для `POST /documents`, отже клієнт має згенерувати та передавати ключ | Додатковий крок у кожному запиті створення | Надійність > Зручність | Це поточний контракт; довжина ключа — 1–128 символів. Тести перевіряють пропущений і граничні ключі. |
| **Консистентність ↔ Доступність** | Паралельне редагування одного документа може порушити цілісність позицій; координації конкурентних змін немає | Ризик не виміряно конкурентним тестом | Консистентність > доступність під час конфлікту | Поточний API не має механізму блокувань/версій; уникати обіцянок атомарної спільної роботи. |

### 5.2 Матриця пріоритетів атрибутів

| Атрибут якості | Вимога (FR/NFR) | Вага (1-5) | Поточний стан | Метрика |
|---|---|---|---|---|
| Безпека | NFR-SEC-001–005 | **5** | IAM, сесійна автентифікація, доступ до документа та валідація реалізовані; тестове покриття конкретне | Відповідні 401/403/422 і security scheme |
| Надійність | NFR-REL-001–003 | **5** | Повтори і читання після запису перевіряються в межах процесу; довговічність і конкурентність не забезпечені | Повтор без дубліката; дані після рестарту; неперервність позицій |
| Продуктивність | NFR-PERF-001–006 | **4** | Locust/Prometheus доступні; збережений RPS 20,58 нижчий за ціль 500, параметри прогону невідомі | p95 < 150 мс; ≥ 500 req/s; відповідь < 500 КБ |
| Доступність | NFR-AVAIL-001 | **4** | Метрики запитів налаштовані; 30-денне SLO та резервування не підтверджені | ≥ 99,9% за 30 днів |

## 6. Сценарії атрибутів якості (Quality Attribute Scenarios)

### Сценарій S-PERF-001: Час відповіді при пікових навантаженнях

**Контекст:** цільовий навантажувальний профіль для API; реалізація в репозиторії є прототипом зі сховищем у пам'яті.

| Елемент | Значення |
|---------|----------|
| **Стимул** | `GET /documents?limit=100&offset=0` від 100 одночасних клієнтів |
| **Артефакт** | API Gateway + компонент Docs |
| **Оточення** | 10 або більше одночасних користувачів протягом 5 хвилин; конкретне production-середовище в репозиторії не задане |
| **Відповідь системи** | 200 із першою сторінкою, p95 < 150 мс |
| **Вимірювання** | Запуск `loadtests/locustfile.py` з потрібними користувачами/тривалістю та p95 із Locust або Prometheus; наявні артефакти не містять доказу саме цього профілю. |
| **Умова провалу** | p95 ≥ 150 мс АБО хоча б один запит повертає 5xx |

### Сценарій S-SEC-002: Спроба несанкціонованого доступу

**Контекст:** користувач A намагається отримати документ користувача B без дозволу.

| Елемент | Значення |
|---------|----------|
| **Стимул** | (а) `GET /api/v1/documents` без токена сесії; (б) `GET /api/v1/documents/{id}` з дійсним токеном користувача без доступу до цього документа |
| **Артефакт** | Компонент IAM + компонент Docs |
| **Оточення** | Production |
| **Відповідь системи** | (а) 401 Unauthorized; (б) 403 Forbidden без вмісту документа. Відсутній/недійсний токен журналюється механізмом IAM; окреме журналювання авторизованої спроби без дозволу тут не заявляється. |
| **Вимірювання** | `tests/api/test_documents_api.py::test_without_token_documents_are_closed`, `::test_missing_and_foreign_documents_look_the_same` і наскрізний `::test_prototype_story` перевіряють відмову в доступі. |
| **Умова провалу** | Будь-яка спроба без токена повертає не 401, або користувач без дозволу отримує 2xx чи вміст документа. |

### Сценарій S-REL-003: Повторне створення документа з ключем ідемпотентності

**Контекст:** клієнт повторює запит створення документа під час роботи того самого процесу.

| Елемент | Значення |
|---------|----------|
| **Стимул** | Два `POST /api/v1/documents` з однаковим обов'язковим `Idempotency-Key` і назвою; окремо повторне використання ключа з іншою назвою. |
| **Артефакт** | Маршрут створення документа та його in-memory `idempotency_records`. |
| **Оточення** | Один процес; ключі зберігаються лише в пам'яті та не мають TTL. |
| **Відповідь системи** | Перший запит повертає 201; повтор із тією самою назвою повертає 201 і той самий документ; інша назва з тим самим ключем повертає 409. |
