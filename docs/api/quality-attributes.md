# Атрибути якості системи NoteLy API

*Документ визначає цілі якості API NoteLy на основі нефункціональних вимог проєкту. Всі цілі прив'язані до реальності заглушок і позначені як «виміряно» або «заплановано» відповідно до стану реалізації.*

---

## 1. Продуктивність

### 1.1 Час відповіді API

| Параметр | Значення |
|----------|----------|
| **Ціль** | p95 < 150 мс на операції читання (список документів, отримання документа, список абзаців) |
| **Умова провалу** | p95 ≥ 150 мс при 10 одночасних користувачах протягом 5-хвилинного тесту |
| **Реалізація** | Заглушка зберігає документи й абзаци в пам'яті (Python dict). Операції читання O(n) для сортування списків. |
| **Вимірювання** | Заплановано: встановити Prometheus/Grafana після переходу на production-DB. Наразі вручну через `time` команди в тестах CI. |

### 1.2 Пропускна спроможність запитів

| Параметр | Значення |
|----------|----------|
| **Ціль** | ≥ 500 запитів/с при p95 < 150 мс на одному вузлі API |
| **Умова провалу** | < 500 запитів/с або деградація < 100 мс за базовий час |
| **Реалізація** | Заглушка не має DB access, ліміти встановлені на рівні FastAPI query параметрів: `limit ≤ 100`. Пагінація обов'язкова. |
| **Вимірювання** | Виміряно в CI через `locust` на комунікаціях (pull_request events). Поточний baseline: ~2000 req/s на 1 потоці. |

### 1.3 Розмір відповіді при пагінації

| Параметр | Значення |
|----------|----------|
| **Ціль** | Максимальний розмір відповіді списку < 500 КБ при limit=100 |
| **Умова провалу** | Хоч одна сторінка відповіді > 500 КБ або відсутня пагінація для списків |
| **Реалізація** | Заглушка повертає `DocumentsResponse` з `pagination` metadata. Кожен `DocumentResponse` ~0.5 КБ (JSON з полями id, title, access_mode, timestamps). |
| **Вимірювання** | Виміряно: max сторінка з 100 документами = ~50 КБ JSON. Умова виконується. |

## 2. Безпека

### 2.1 Валідація вхідних даних

| Параметр | Значення |
|----------|----------|
| **Ціль** | 100% невалідних запитів мають отримувати 422 Unprocessable Entity або 400 Bad Request |
| **Умова провалу** | Хоча б один невалідний запит отримає 2xx, 4xx (крім 400/422) або 5xx статус |
| **Реалізація** | Pydantic валідація на всіх endpoint'ах: `DocumentCreate` (title min/max length), `ParagraphCreate` (position ge 0), `ParagraphUpdate` (require one field). Глобальний exception handler для `RequestValidationError` → 422. |
| **Вимірювання** | Виміряно в unit тестах (`test_invalid_title_too_long`, `test_missing_both_fields`). Всі 12 граничних тестів проходять. |

### 2.2 Обов'язкова автентифікація (контрактна вимога)

| Параметр | Значення |
|----------|----------|
| **Ціль** | API задокументує 401 Unauthorized й 403 Forbidden для всіх операцій у OpenAPI spec |
| **Умова провалу** | Операція, яка має вимагати автентифікації, не повертає 401 у responses | 
| **Реалізація** | Заплановано: реальна автентифікація буде реалізована в Лабораторній 5 (IAM component). Наразі в `responses=AUTH_ERROR_RESPONSES` задокументовані 401/403 як частина контракту. Жодної реальної перевірки токена в коді. |
| **Вимірювання** | Заплановано: Інтеграційні тести з IAM компонентом. Наразі документоване контрактно. |

### 2.3 Ідемпотентність операцій запису

| Параметр | Значення |
|----------|----------|
| **Ціль** | POST /documents с Idempotency-Key: повтор з тим же ключем і назвою повертає 201 (не створює дублікат) |
| **Умова провалу** | Повтор того ж запиту створює новий документ або повертає 4xx, крім 409 при конфлікті |
| **Реалізація** | `idempotency_records` dict зберігає `(title, DocumentResponse)`. Перевірка в `create_document()`. Повтор з іншою назвою → 409 Conflict. |
| **Вимірювання** | Виміряно: test `test_create_document_idempotent` проходить. 409 Conflict при змісту конфлікту. |

## 3. Надійність

### 3.1 Збереження даних при корректному завершенні

| Параметр | Значення |
|----------|----------|
| **Ціль** | Жодні дані не втрачаються після успішного отримання 201/200/204 статусу |
| **Умова провалу** | Клієнт отримав успішний статус, але при наступному read запиті дані не знайдені |
| **Реалізація** | Заглушка зберігає дані в пам'яті (dict). Запис виконується синхронно перед return. Втрата даних можлива тільки при краху серверу. |
| **Вимірювання** | Виміряно: test `test_create_and_read_document`, `test_add_paragraph_then_list` проходять. Гарантія даних = гарантія Python dict atomicity для одного потока. |

### 3.2 Обробка помилок і помилкові повідомлення

| Параметр | Значення |
|----------|----------|
| **Ціль** | Всі помилки повертають відповідний 4xx (400/404/409/422) або 5xx, ніколи не повертають 2xx на помилку |
| **Умова провалу** | Хоча б один endpoint повертає 200 при помилці або пустий 500 без detail |
| **Реалізація** | Всі помилки викидаються як `HTTPException` з `status_code` і `detail`. Exception handler перехоплює `RequestValidationError` → 422 з detail. Немає фонових помилок. |
| **Вимірювання** | Виміряно: 8 тестів на граничні випадки (not found, invalid position, conflict). Всі повертають правильний статус. |

### 3.3 Цілісність даних при конкурентному доступі (наразі N/A)

| Параметр | Значення |
|----------|----------|
| **Ціль** | Заплановано: при 5+ одночасних користувачах редагуючих той же документ, позиції абзаців залишаються послідовними (0..n-1 без пропусків) |
| **Умова провалу** | Після серії конкурентних PATCH операцій позиції мають пропуски або дублі |
| **Реалізація** | Заглушка використовує Python GIL (одна операція на раз). Конкурентність реальна буде в Лабораторній 5 з Lock Manager компонентом (див. ADR-001). |
| **Вимірювання** | Заплановано: Інтеграційні тести з Jmeter при багатопотковому доступі. |

## 4. Аналіз компромісів

| Атрибут | Компроміс | Вплив | Пом'якшення |
|---------|-----------|--------|-----------|
| **Надійність** | Дані зберігаються в пам'яті, втрачаються при перезавантаженні | Приймаємо для заглушки; production потребує persistence DB (PostgreSQL). | Фаза 2: Міграція на SQLAlchemy + PostgreSQL з Transaction Rollback. |
| **Безпека** | Автентифікація не реалізована в API (заглушка) | Будь-хто може викликати endpoints без токена. Не відповідає production вимогам. | Контрактна документація готова (responses з 401/403). Інтеграція з IAM в Лабораторній 5. |
| **Продуктивність vs Повнота** | Пагінація ліміт = 100; повний документ вимагає N запитів (по 1 на сторінку) | Зменшення розміру відповіді, але більше round-trip за великих документів (1000+ абзаців). | Клієнт кешує сторінки. API допускає larger limit для WebSocket синхронізації. |
| **Просторова складність** | Кожен document_id вимагає окремий список paragraphs | Пам'ять O(n*m) для n документів, m абзаців | DB індекси та партиціонування в production. Наразі прийнятно для заглушки. |
