Для помилок нижче API повертає JSON-об’єкт із полем detail (ApiError). Захищені маршрути авторизуються через заголовок Authorization зі схемою Bearer і токеном доступу. Список можливих помилок описує контракт маршруту; помилки інфраструктури не оголошені як окремі API-відповіді.

### Спільні примітки щодо помилок

- Відповідь валідації `422` у застосунку має вигляд `{"detail":"Некоректні вхідні дані."}` або повідомлення доменного правила. Масив помилок із прив'язкою до окремих полів API не повертає.
- `503`, тайм-аут і мережевий збій не описані як відповіді цих маршрутів; клієнт може окремо обробляти фактичний HTTP `503`, тайм-аут або відсутність з'єднання, але не повинен вважати їх задекларованими API-кодами.
- `GET /api/v1/documents/trash` фільтрує список за правом `TRASH`, тому для користувача без цього права може повернути порожню сторінку, а не відмову `403`. Операція відновлення перевіряє право й може повернути `403`.
- Успішні й помилкові JSON-відповіді наведені за Pydantic-моделями, обробниками помилок і деклараціями маршрутів. `204` не має тіла.
- Поточна роль користувача доступна через список учасників тільки власнику документа. Для Editor і Guest endpoint списку ролей повертає однаковий `403`; `DocumentResponse` не містить ролі. У frontend невідому роль трактуємо як режим читання (редагування, переміщення в кошик і керування порядком вимкнені), щоб не показувати непідтверджені дозволи. Це також означає, що Editor не може редагувати через поточний frontend до появи endpoint власної ролі.

## Календар

Усі маршрути нижче потребують Bearer-токен. Помилки повертаються як `{"detail":"..."}`; коди, заявлені в OpenAPI, наведені в таблиці.

| Метод | Маршрут | Тіло запиту / параметри | Успішна відповідь | Помилки |
|---|---|---|---|---|
| `GET` | `/api/v1/calendar/events` | Query: обов'язкові `start_at` і `end_at` у форматі ISO 8601 з часовим поясом; без тіла | `200`: масив `EventResponse` | `401`, `403`, `404`, `422` |
| `POST` | `/api/v1/calendar/events` | `{"title":"...","start_at":"...","end_at":"..."}`; дати мають містити часовий пояс, завершення — бути пізніше за початок | `201`: `EventResponse` | `401`, `403`, `404`, `422` |
| `GET` | `/api/v1/calendar/events/{event_id}` | Без тіла; додатний `event_id` | `200`: `EventResponse` | `401`, `403`, `404`, `422` |
| `PATCH` | `/api/v1/calendar/events/{event_id}` | Одне або більше полів: `{"title":"...","start_at":"...","end_at":"..."}` | `200`: оновлений `EventResponse` | `401`, `403`, `404`, `422` |
| `DELETE` | `/api/v1/calendar/events/{event_id}` | Без тіла | `204`, без тіла | `401`, `403`, `404`, `422` |
| `GET` | `/api/v1/calendar/events/{event_id}/participants` | Без тіла | `200`: масив `{"user_id":"...","name":"...","email":"..."}` | `401`, `403`, `404`, `422` |
| `PUT` | `/api/v1/calendar/events/{event_id}/participants` | `{"email":"повний email"}` | `204`, без тіла | `401`, `403`, `404`, `422` |
| `DELETE` | `/api/v1/calendar/events/{event_id}/participants/me` | Без тіла | `204`, без тіла | `401`, `403`, `404`, `422` |
| `DELETE` | `/api/v1/calendar/events/{event_id}/participants/{participant_id}` | Без тіла; `participant_id` — UUID | `204`, без тіла | `401`, `403`, `404`, `422` |
| `PUT` | `/api/v1/calendar/events/{event_id}/document` | `{"document_id":1}` | `200`: оновлений `EventResponse` | `401`, `403`, `404`, `422` |
| `DELETE` | `/api/v1/calendar/events/{event_id}/document` | Без тіла | `200`: оновлений `EventResponse` | `401`, `403`, `404`, `422` |

`EventResponse` містить `id`, `creator_id`, `creator_name`, `creator_email`, `title`, `start_at`, `end_at`, `document_id`, `created_at` і `updated_at`. `creator_name` та `creator_email` — ім'я й email автора; значення можуть бути `null`, якщо обліковий запис автора не знайдено.

Редагувати або видаляти подію, керувати її учасниками й прив'язаним документом може лише автор події (`creator_id`). Учасник може переглядати подію та вийти з неї через маршрут `/participants/me`; він не може змінювати або видаляти подію чи керувати іншими учасниками або документом.

`GET /api/v1/calendar/events/{event_id}/participants` повертає масив `[{ "user_id": "...", "name": "...", "email": "..." }]`. Автор події до цього списку не входить: його профільні дані містяться у `creator_name` та `creator_email`.

Пошуку користувачів для підказок email API не має. Автор додає учасника лише за повною email-адресою через `PUT .../participants`; якщо адреса не зареєстрована, API повертає `404`.

Створення події з додатковими учасниками й документом виконується послідовно кількома запитами: спочатку `POST /api/v1/calendar/events`, потім окремий `PUT .../participants` для кожного email, а насамкінець — за наявності вибраного документа — `PUT .../document`. Додаткові учасники та документ не входять до тіла `POST`. Якщо створення події не вдалося, діалог лишається відкритим із введеними даними для повторної спроби. Якщо подію вже створено, але один із наступних запитів не вдався, подія не видаляється: frontend продовжує інші запити, оновлює календар і показує, який email не вдалося додати (зокрема, `404` означає, що користувача не знайдено) та/або який документ не вдалося прив’язати.

## Відкладені або не підключені функції

У модулях 02–04 ці пункти або не мають відповідних API-маршрутів, або їхній UI ще не входить до реалізованого сценарію. Елементи не повинні надсилати непідтримувані запити чи створювати враження, що дія успішно виконана. Наявні API-сценарії, які входять до реалізованого сценарію, описані в таблиці вище.

1. **Роль та ім'я власника.** Макети показують роль користувача й власника в документах і робочому просторі. Поточна відповідь `DocumentResponse` не містить цих даних, а список учасників доступний тільки Owner. Живий фронтенд не вгадує роль і не показує вигадані імена; дії доступу все одно перевіряє сервер, а `403` обробляється як помилка прав.
2. **Запрошення незареєстрованого користувача.** Макет показує екран-запрошення і продовження після реєстрації. Немає endpoint створення/прийняття запрошення та безпечного токена/прив'язки документа; `PUT .../access` додає лише вже зареєстрований email. Екран `frontend/invitation.html` є лише візуальним, а його дія неактивна: не підключати його до API, реєстрації чи URL-параметрів.
3. **Запит ролі Editor.** Макет Guest показує дію запиту ролі редактора. Є лише запит на доступ без тіла (`POST .../access/requests`); окремого підтриманого сценарію запиту ролі у REST немає. Кнопку можна показати як неактивний/демонстраційний макет, без POST.
4. **Керування доступом Owner.** Реалізовано UI додавання зареєстрованого учасника, зміни ролі, відкликання доступу та перегляду/підтвердження/відхилення запитів через наявні Owner endpoints. API запитів повертає лише `requester_id`, без імені чи email; UI показує доступний ідентифікатор. Кнопка «Доступ» активна лише для Owner. Перемикання режиму доступу поки неактивне: запит до `/access/mode` не викликається.
5. **Запит доступу без доступу до документа.** Реалізовано перевірку власних запитів, надсилання запиту на доступ і стани очікування/відхилення/помилки. Якщо документ уже доступний, показується звичайна сторінка документа. Запит саме ролі Editor не підтримується: кнопка лишається неактивною.
6. **Форматування редактора.** Макет містить H1, жирний, курсив, списки й цитату. API зберігає тільки `content` як рядок до 10 000 символів і не визначає формат серіалізації. Панель форматування відображається візуально, але залишається неактивною; frontend зберігає лише звичайний текст абзаців і не кодує форматування.
7. **Історія та відновлення версій.** Макети містять історію версій, порівняння й відновлення, але REST endpoint-ів для версій немає. Їх можна показати як демонстраційні, без запитів і без повідомлення про реальне збереження/відновлення.
8. **Остаточне видалення документа.** У макеті кошика є «Видалити назавжди», але API підтримує лише переміщення в кошик через `DELETE /api/v1/documents/{document_id}`; остаточне видалення виконує планувальник через 30 днів. Кнопка в інтерфейсі лишається неактивною — викликати непідтримуваний API-запит не можна.
9. **Польові помилки відповіді.** Макети показують помилку біля конкретного поля, але API повертає `{"detail":"..."}`, не структурований список полів. Інтерфейс може локально перевірити відомі обмеження і показувати відомі серверні причини на відповідному полі; довільний `422` відображати загально, не вигадуючи поля з відповіді.
10. **503 і помилки мережі.** `503` не оголошений як відповідь маршрутів. У макетах можна мати візуальні стани недоступності/повтору, але конкретні API-дії підключати лише до реально отриманого статусу/мережевого збою. Користувачу не показувати сирий текст бекенду.
11. **CORS.** До кроку 0.5 у `src/api/main.py` не було `CORSMiddleware` і в репозиторії не було `.env.example`. У кроці 0.5 додано `CORS_ALLOWED_ORIGINS` (перелік origin через кому, wildcard заборонений), методи `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, заголовки `Authorization`, `Content-Type`, `Idempotency-Key`, доступ браузера до відповіді `Retry-After`, приклад `http://localhost:3000` у `.env.example` та тести preflight, дозволених заголовків відповіді, забороненого origin і wildcard.
