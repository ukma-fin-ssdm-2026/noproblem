Для помилок нижче API повертає JSON-об’єкт із полем detail (ApiError). Захищені маршрути авторизуються через заголовок Authorization зі схемою Bearer і токеном доступу. Список можливих помилок описує контракт маршруту; помилки інфраструктури не оголошені як окремі API-відповіді.

### Спільні примітки щодо помилок

- Відповідь валідації `422` у застосунку має вигляд `{"detail":"Некоректні вхідні дані."}` або повідомлення доменного правила. Масив помилок із прив'язкою до окремих полів API не повертає.
- `503`, тайм-аут і мережевий збій не описані як відповіді цих маршрутів; клієнт може окремо обробляти фактичний HTTP `503`, тайм-аут або відсутність з'єднання, але не повинен вважати їх задекларованими API-кодами.
- `GET /api/v1/documents/trash` фільтрує список за правом `TRASH`, тому для користувача без цього права може повернути порожню сторінку, а не відмову `403`. Операція відновлення перевіряє право й може повернути `403`.
- Успішні й помилкові JSON-відповіді наведені за Pydantic-моделями, обробниками помилок і деклараціями маршрутів. `204` не має тіла.
- Поточна роль користувача доступна через список учасників тільки власнику документа. Для Editor і Guest endpoint списку ролей повертає однаковий `403`; `DocumentResponse` не містить ролі. У frontend невідому роль трактуємо як режим читання (редагування, переміщення в кошик і керування порядком вимкнені), щоб не показувати непідтверджені дозволи. Це також означає, що Editor не може редагувати через поточний frontend до появи endpoint власної ролі.

## Відкладені або не підключені функції

У модулях 02–04 ці пункти або не мають відповідних API-маршрутів, або їхній UI ще не входить до реалізованого сценарію. Елементи не повинні надсилати непідтримувані запити чи створювати враження, що дія успішно виконана. Наявні API-сценарії, які входять до реалізованого сценарію, описані в таблиці вище.

1. **Роль та ім'я власника.** Макети показують роль користувача й власника в документах і робочому просторі. Поточна відповідь `DocumentResponse` не містить цих даних, а список учасників доступний тільки Owner. Живий фронтенд не вгадує роль і не показує вигадані імена; дії доступу все одно перевіряє сервер, а `403` обробляється як помилка прав.
2. **Запрошення незареєстрованого користувача.** Макет показує екран-запрошення і продовження після реєстрації. Немає endpoint створення/прийняття запрошення та безпечного токена/прив'язки документа; `PUT .../access` додає лише вже зареєстрований email. Екран `frontend/invitation.html` є лише візуальним, а його дія неактивна: не підключати його до API, реєстрації чи URL-параметрів.
3. **Запит ролі Editor.** Макет Guest показує дію запиту ролі редактора. Є лише запит на доступ без тіла (`POST .../access/requests`); окремого підтриманого сценарію запиту ролі у REST немає. Кнопку можна показати як неактивний/демонстраційний макет, без POST.
4. **Керування доступом Owner.** API підтримує перегляд/зміну учасників і ролей та зміну режиму доступу. UI цих Owner-операцій ще не входить до реалізованого frontend-сценарію: кнопка «Доступ» вимкнена, ці API-маршрути не викликаються.
5. **Форматування редактора.** Макет містить H1, жирний, курсив, списки й цитату. API зберігає тільки `content` як рядок до 10 000 символів і не визначає формат серіалізації. Панель форматування відображається візуально, але залишається неактивною; frontend зберігає лише звичайний текст абзаців і не кодує форматування.
6. **Історія та відновлення версій.** Макети містять історію версій, порівняння й відновлення, але REST endpoint-ів для версій немає. Їх можна показати як демонстраційні, без запитів і без повідомлення про реальне збереження/відновлення.
7. **Остаточне видалення документа.** У макеті кошика є «Видалити назавжди», але API підтримує лише переміщення в кошик через `DELETE /api/v1/documents/{document_id}`; остаточне видалення виконує планувальник через 30 днів. Кнопка в інтерфейсі лишається неактивною — викликати непідтримуваний API-запит не можна.
8. **Польові помилки відповіді.** Макети показують помилку біля конкретного поля, але API повертає `{"detail":"..."}`, не структурований список полів. Інтерфейс може локально перевірити відомі обмеження і показувати відомі серверні причини на відповідному полі; довільний `422` відображати загально, не вигадуючи поля з відповіді.
9. **503 і помилки мережі.** `503` не оголошений як відповідь маршрутів. У макетах можна мати візуальні стани недоступності/повтору, але конкретні API-дії підключати лише до реально отриманого статусу/мережевого збою. Користувачу не показувати сирий текст бекенду.
10. **CORS.** До кроку 0.5 у `src/api/main.py` не було `CORSMiddleware` і в репозиторії не було `.env.example`. У кроці 0.5 додано `CORS_ALLOWED_ORIGINS` (перелік origin через кому, wildcard заборонений), методи `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, заголовки `Authorization`, `Content-Type`, `Idempotency-Key`, доступ браузера до відповіді `Retry-After`, приклад `http://localhost:3000` у `.env.example` та тести preflight, дозволених заголовків відповіді, забороненого origin і wildcard.

## Умови підключення відкладених функцій

Коли бекенд реалізує будь-яку відкладену функцію або відповідний UI буде доданий до обсягу роботи, оновити таблицю контракту за фактичним OpenAPI та підключати лише підтверджені сценарії. Не створювати клієнтський endpoint, тіло запиту, формат вмісту чи успішний стан наперед.
