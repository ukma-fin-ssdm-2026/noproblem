## 4. Виявлені потенційні вразливості

### 4.1. Немає обмеження довжини тексту абзацу

**Як знайдено.** Ручний огляд коду; Bandit правила для цього не має.

**Суть.** Для тексту абзацу документа не задано верхньої межі довжини, тож клієнт може надіслати
дуже великий текст.

**Класифікація.** OWASP API Security Top 10 2023 — API4 Unrestricted Resource Consumption;
CWE-770 (Allocation of Resources Without Limits or Throttling).

**Ризик.** Великі запити споживають пам'ять процесу (дані зберігаються в пам'яті), що може
призвести до відмови в обслуговуванні.

**Рішення.** [вкажіть: виправлено (що саме: ліміт у схемі запиту, код відповіді) або прийнято з обґрунтуванням]

### 4.2. Ключ ідемпотентності спільний для всіх користувачів

**Де:** `src/api/main.py`, `POST /api/v1/documents`.

**Суть.** Записи ідемпотентності зберігаються за самим `Idempotency-Key`, без прив'язки до
користувача. Якщо інший користувач надішле той самий ключ і ту саму назву, сервер поверне йому
чужий документ (id, назву, дати) без перевірки прав. З іншою назвою він отримає `409`, і це
підтверджує, що такий ключ уже хтось використав.

**Класифікація.** OWASP API Security Top 10 2023 — API1 Broken Object Level Authorization;
CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor). Серйозність низька:
атакувальник має знати або вгадати чужий ключ.

**Як знайдено.** Ручний огляд коду під час додавання ролей доступу (PR #121). Bandit таке
не знаходить, бо це помилка логіки доступу, а не небезпечний виклик функції.

**Виправлення:** PR #<номер> — <посилання на PR>. Запис ідемпотентності шукається за парою
(id користувача, ключ).

**Регресійний тест:** `tests/api/test_documents_api.py::test_idempotency_key_is_per_user`.
На коміті з тестом без виправлення: 1 failed. Після виправлення: passed.

### 4.3. Необмежене зростання сховища в пам'яті (ризик прийнято)

**Як знайдено.** Ручний огляд коду.

**Суть.** Документи й записи ідемпотентності зберігаються в пам'яті процесу (словники) і
ніколи не видаляються, тому обсяг даних зростає разом з кількістю запитів.

**Класифікація.** CWE-770 (Allocation of Resources Without Limits or Throttling).

**Рішення: ризик прийнято.** [перевірте й за потреби підправте обґрунтування] Сховище в пам'яті
є свідомим вибором для навчального проєкту без бази даних. У промисловій версії дані
переносяться в БД, а записи ідемпотентності отримують строк життя (TTL).

## 5. Загроза з `threat-model.md`: R2 (підвищення привілеїв)

**Загроза (R2, компонент IAM / Docs, STRIDE: E — Elevation of Privilege, рівень: висока).**
Користувач із роллю `GUEST` або `EDITOR` змінює запит так, щоб отримати права `EDITOR` або
`OWNER` для документа.

**Контрзахід за моделлю загроз.** Перевіряти роль користувача на сервері перед кожною
операцією й використовувати IAM як єдине джерело правди про доступ.

**Як код їй протистоїть.**

| Механізм | Де | Ефект |
|---|---|---|
| Обов'язковий токен на всіх маршрутах документів | `src/api/security.py`, `src/api/auth/` | без токена відповідь `401` |
| Ролі Owner / Editor / Guest, IAM як єдине джерело правди про доступ | `src/iam/access.py`, `src/iam/models.py` | роль береться з IAM для конкретного документа, а не із запиту клієнта |
| Перевірка ролі на сервері перед кожною операцією | `src/api/access.py` | змінений клієнтом запит не дає прав вищої ролі, відповідь `403` |
| Керування доступом через `PUT/GET/DELETE /api/v1/documents/{id}/access` | `src/api/main.py` | спільний доступ за email, з перевіркою прав |

**Чим підтверджено.** Тести `tests/iam/test_access.py` і `tests/api/test_documents_api.py`.

**Виняток.** Вразливість із розділу 4.2 була єдиним місцем, де чужий документ можна було
отримати в обхід перевірки прав; вона виправляється окремим PR.
